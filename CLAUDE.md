# Phazite

Open-source DAW (AGPL-3.0-or-later) in C++20 on Tracktion Engine + JUCE. It hosts VST3 plug-ins (AU on macOS later). Performance and low resource use matter in both the audio engine and the UI.

## Build

Run every command from the repository root. The presets are the only entry point, and the same two commands work on every OS.

- `cmake --list-presets` shows the presets for this machine: `windows-debug`, `windows-profile` (Release with symbols: for playing, profiling and the benchmarks), `windows-release` on Windows; `linux-debug`, `linux-release`, `linux-asan`, `linux-tsan` on Linux/WSL.
- Configure: `cmake --preset <preset>`. Build: `cmake --build --preset <preset>`. Test: `ctest --preset <preset>`, after a build of the same preset (it runs `phazite_tests` once for each test file, named after it, 4 at once, each with a temporary folder of its own; all passed when it prints `100% tests passed` and exits 0; `-R <name>` runs some files only, `-j <n>` more at once). To run some tests only, call the test executable directly, for example `build\windows-debug\phazite_tests_artefacts\Debug\phazite_tests.exe --test-case="*save*"`.
- Run configure and build as separate commands, each with run_in_background and without redirections or pipes (no `>`, `*>`, `2>&1`, `Tee-Object`): the complete output lands in the task's output file. When a command finishes, check its exit code and search that file case-insensitively for `error` and `warning` (this also catches "CMake Warning"), plus `D9` and `LNK4`. The first configure of a build folder also builds JUCE's `juceaide` helper (1-2 minutes); a full build takes several minutes.
- On Windows the shell is Windows PowerShell 5.1: there is no `&&`/`||`, and `;` does not stop after a failure. Use separate commands, or `A; if ($LASTEXITCODE -eq 0) { B }`. In WSL/Linux the shell is Bash.
- Never run vcvars/VsDevCmd, open a Developer PowerShell, or call `cl`, `link`, `msbuild` or `ninja` directly. MSVC is found by `cmake/toolchains/windows-msvc.cmake`, which wraps `external/WindowsToolchain`.
- After a Visual Studio Build Tools update (new MSVC version) or a toolchain change, reconfigure with `cmake --preset <preset> --fresh`. If that folder still fails, delete `build\<preset>` and configure again.
- Before configuring or building, run `@(Get-Process -Name cmake, ninja -ErrorAction Ignore).Count`. If it prints anything other than 0 and you didn't start those processes (VS Code may be building), ask the user before continuing: two builds in one folder break each other.

## Tools (Windows)

- `tools\setup-windows.cmd` installs or updates every tool (including gitleaks) and turns on this clone's git hooks (`core.hooksPath = .githooks`). A full run needs the user at a UAC prompt and can take up to an hour (a few minutes when everything is current), so start it only when the user asks (as a background command) or ask them to run it. `tools\setup-windows.cmd -CheckOnly` is safe at any time: no admin rights, changes nothing.
- Exit codes (your shell tool shows 3010 as 194; the script's last line, "Result: ...", always states it): 0 = done; 3010 = done, but Windows must restart (ask the user to reboot, then run it again); 1 = a step failed (read the FAILED lines and the log path it prints); 2 = it could not start. With `-CheckOnly`: 0 = all present, 1 = something missing (including this clone's git hooks) or not on this shell's PATH, 3010 = Visual Studio is waiting for a reboot. Switches: `-CheckOnly`, `-SkipUpdates`, `-WithTestPlugin` (Surge XT), `-WithLlvm`, `-SkipVSCodeExtensions`.
- If `cmake` or `git` is "not recognized", run `tools\setup-windows.cmd -CheckOnly`. If it finds the tools, the program that started Claude Code has an old PATH: ask the user to quit every VS Code window, start VS Code from the Start menu and close any terminals it restores (or to open a new terminal and start Claude there). If it reports MISSING, ask the user to run the setup. Don't edit PATH or search the disk for tools. If it prints `hooks ... OFF`, the git hooks are off in this clone: tell the user, then run `git config core.hooksPath .githooks` (no admin rights or full setup needed).

## Running and debugging

- The app is `build/<preset>/Phazite_artefacts/<build type>/Phazite` (`.exe` on Windows), where the build type is `Debug` for `*-debug` and `linux-asan`, `Release` for `*-release`, and `RelWithDebInfo` for `windows-profile` and `linux-tsan`. Run the TSan build as `TSAN_OPTIONS=suppressions=tools/tsan-suppressions.txt setarch $(uname -m) -R build/linux-tsan/Phazite_artefacts/RelWithDebInfo/Phazite`. That file lists known races in Tracktion, each explained in `docs/realtime-audit.md`; a race in Phazite's own code is fixed, never suppressed. The linux-asan tests suppress known leaks in JUCE and Tracktion the same way (`tools/lsan-suppressions.txt`, each explained there).
- The app is for the user to run, or to start with F5 in VS Code. Don't start it from the shell unless asked; then use `Start-Process <path>` (a bare call blocks the tool until the window closes). Tell the user what to click and listen for.
- Debugging: VS Code's "Phazite (Windows)" launch configuration (F5) builds the active preset and starts the app under the debugger. A crash outside a debugger leaves a dump in `%LOCALAPPDATA%\CrashDumps\Phazite.exe.*.dmp`; open it with the "Open crash dump (Windows, Debug build)" configuration. Only `windows-debug` and `windows-profile` builds have symbols, so reproduce Release crashes in one of those.
- VS Code configures only on request. After a build folder was created from the shell (first configure, or after deleting `build\<preset>`), ask the user to run "CMake: Configure" once in VS Code so IntelliSense and F5 know about it.
- LNK1104 on Phazite.exe means the app, its `--PluginScan` child or a debug session is still running: ask the user to close it.

## Real-time rules (audio thread)

The audio thread is the audio callback and everything it calls: plug-in and graph processing (`applyToBuffer`, `process`, `processBlock`), Tracktion node processing, and any helper reached from them. On the audio thread:
- No memory allocation or release: no `new`/`delete`/`malloc`, no growing `std::vector`/`juce::Array`, no creating `std::string`/`juce::String`, no allocating `std::function` captures. Allocate up front when preparing.
- No locks or waiting: no `std::mutex`, `juce::CriticalSection`/`ScopedLock`, condition variables, `WaitableEvent`, `MessageManagerLock`, or blocking calls into other threads.
- No posting to the message thread: no `triggerAsyncUpdate`, `sendChangeMessage` or `juce::MessageManager::callAsync` (they lock or allocate). Set an atomic flag instead and poll it from a `juce::Timer`.
- No file or network I/O, no logging (`DBG`, `juce::Logger`, `std::cout`), no system calls that can block.
- No throwing exceptions, no unbounded loops.
- Threads communicate through lock-free queues (single-producer/single-consumer FIFOs such as `juce::AbstractFifo` or `choc::fifo::SingleReaderSingleWriterFIFO`) and lock-free `std::atomic` values (add `static_assert (std::atomic<T>::is_always_lock_free)` for anything wider than a pointer), not shared mutable state.
- Read parameters through their atomic value (`AutomatableParameter::getCurrentValue()`), never through `juce::ValueTree`, `juce::CachedValue` or other message-thread objects.
- Tracktion's own instruments and effects (its 4OSC synth, reverb, EQ, compressor, sampler...) lock and allocate on the audio thread, so Phazite doesn't use them: the device list (`phazite::getDeviceTypes()`) offers Phazite's own devices and the plug-ins found by scanning, and code and tests use those. Phazite's devices follow these rules, and each has a guarded scenario in the real-time audit.
- Tracktion's own code breaks some of these rules; `docs/realtime-audit.md` lists what is known and what Phazite does about each. After changes that touch playback, run the audit (`phazite_tests.exe --test-suite=realtime-audit` from the `windows-debug` build): it counts allocations on the audio thread and shows where they come from. Its guarded scenarios fail if steady playback allocates.

## Architecture rules

The code is layered so that the UI can change without touching the rules of editing, every edit can be tested without a window, and parts of the engine could be replaced later (`docs/design.md`, section 24). The roadmap's architecture track (phases A0 to A5) moves the existing code there; new code follows these rules now.
- Dependencies point down: `src/app/` may include `ui/`, `services/` and `model/`; `src/ui/` may include `services/` and `model/`; `src/services/` may include `model/`; `src/model/` includes none of them, but `engine/`, Phazite's playback engine, which includes only `devices/`, and `sandbox/`, what Phazite shares with the helpers that host plug-ins, which includes only `devices/` too. `src/host/`, the helper program, includes `sandbox/` and `devices/`, and no layer includes it. Every layer may include `devices/`, which includes none of the others. Tests and tools may include anything.
- No window code below the UI: `src/model/`, `src/services/`, `src/engine/`, `src/sandbox/` and `src/devices/` include no JUCE window module (`juce_gui_basics`, `juce_gui_extra`) and name no window class (`juce::Component`, `juce::KeyPress`...); `juce_graphics`, for `juce::Colour` values, is allowed in the model and services for now. Key and mouse handling, pixel sizes and how values are shown belong in `src/ui/`.
- Devices, the engine and the sandbox are engine-neutral: `src/devices/`, `src/engine/`, `src/sandbox/` and the helper program, `src/host/`, include no Tracktion header (nor the model's prelude) and name no `te::` type. A device's thin Tracktion plug-in, in the model, hands it the audio, the notes and the parameters' current values through the engine's `DeviceRunner`; the model compiles the song into what Phazite's engine plays.
- The UI decides nothing about the project: UI code doesn't start undo steps or change the project; it runs a command or calls a model function, and a control changes a parameter through a `ParameterHandle`. Phase A2 moves the UI's remaining undo steps and edits into the model.
- Tracktion stays in the model: `src/ui/` names no `te::` type and includes neither Tracktion nor a model `internal/` header (since phase A3, `phazite_ui` compiles without Tracktion's include path), and doesn't hide Tracktion behind `auto` or aliases: the aim is a UI that doesn't depend on Tracktion, not a lower count. Call a model function that takes and returns Phazite's own types (IDs, plain values), and add one, with a test, if there is none. A model header that names a Tracktion type goes in its area's `internal/` folder; the model's other headers stay free of Tracktion.
- Every change to a project is one named undo step with one owner: a command (through `undoTarget`; the registry opens the step), or a model function that is a change of its own (its comment says so, as `addDeviceTo()`'s does), which begins with `phazite::UndoStep` (`src/model/commands/internal/Undo.h`). Other model functions pass the song's undo history (`Song::getUndoManager()`, `src/model/base/Song.h`, from an Edit through `getSong()`; never the Edit's own, `te::Edit::getUndoManager()`, which only records what the mirror tells Tracktion) and never begin a step, so their changes join the caller's step; an `UndoStep` begun inside another for the same song joins it. A change that spans several events, such as a drag, is a `phazite::Gesture` (`Undo.h`): one named step from its start to its commit, which `UndoStep`s begun meanwhile join, or rolled back (`rollBack()`, meant for Escape during a drag, which no tool handles yet) leaving nothing to redo. View state is written without an undo manager. A command that moves the selected time range to what it made moves it with `RangeSelection::setInUndoStep()`, so that Undo puts it back; a range selected by hand isn't an undo step. What a new project starts with is added through `Project::create()`'s content function, which saves it and opens the project from that save, so it is neither an undo step nor an unsaved change. Changes that are deliberately not undo steps (mute and solo, freezing a track, the loop, view state) are model functions too. Containers' rack types are added without undo steps and stay for the session, and a project drops those no container plays when it opens (`model/mixer/internal/Containers.h` says why).
- View state (track heights, collapsed and pinned tracks, drum mode and drum rows, both editors' grid settings) is saved, but written without an undo step and doesn't count as an unsaved change (decision 4). Two lists say what it is, and must stay exact: `schema::isTrackViewProperty()`, `isGridProperty()` and the PIANOROLL element in `Schema.h`, and `Project`'s `isUncountedProperty()` / `isUncountedElement()`, which use them for notifications and the comparison with the saved copy alike.
- Every name Phazite writes into a project file is defined once, in `src/model/base/internal/Schema.h`, with where it is stored and what it holds; read and write Phazite's data only through those names and the song (`Song::getState()`, from an Edit through `getSong()`) or `findPhaziteState()`. A device's type and parameter IDs, in its description in `src/devices/`, are saved too (`Schema.h` says how; a choice's value is saved as its number). Save Phazite's own values (names or Phazite's enums), never a Tracktion enum number.
- No backward compatibility while Phazite is pre-alpha (the owner's decision, 2026-10-18; `docs/design.md`, section 18): projects, presets and settings saved by an earlier build needn't open or keep what they held. So there are no format versions or migrations, and no code, tests or comments kept for what earlier builds saved or played; remove such leftovers as you find them. Rename or reorder anything saved (names in `Schema.h`, device and parameter IDs, a choice's order, settings keys) when that makes the code clearer, regenerate the golden files, and say why in the commit message. The owner will say when compatibility starts; until then, don't add version checks or upgrade paths.
- Phazite's own settings (the `phazite*` keys) are read and written only through `phazite::Settings` (`src/services/Settings.h`), which lists every key once with its default and when it is saved; a new setting goes into that list.
- Every colour, size, corner radius and font in the UI comes from the design tokens (`DesignTokens.h`, read with `ui::getPalette (component)`); if none fits, add a token rather than a literal. Phase A4 moves the tokens into a file a designer edits, with a gallery app, and the text the user reads into a strings table.
- Meters, the playhead and other values that change many times a second are read from small read-only sources polled by the displays' ticker (`ui::DisplayTicker`), a `juce::Timer` or, for the playhead while playing, the display's frames (`juce::VBlankAttachment`), never stored in the project or sent as change messages. A display repaints only when what it draws moved (`ui::DrawnNumbers`): in silence, with nothing turned, nothing repaints. A component that paints all of itself in opaque colours says so (`setOpaque (true)`), so that what is behind it doesn't repaint with it; and a view of many items (the playlist's clips) makes components only for those in view.
- `tools/check-architecture.sh` counts what these rules forbid in `src/`, plus Tracktion includes in the model outside its prelude, the model's `internal/` headers included in the UI, undo steps begun in the model outside the undo code, model files on include loops, files directly in `src/model/`, `src/ui/`, `src/engine/`, `src/sandbox/`, `src/host/` or `src/devices/`, Tracktion in `src/engine/`, `src/sandbox/` and `src/host/` (`engine-tracktion`, `sandbox-tracktion`, `host-tracktion`), `#include "..."` lines in `src/`, `tests/` and `tools/` that name no file exactly, and source paths in `CMakeLists.txt` that name no file exactly or C/C++ files it doesn't list (Windows forgives a wrong case or a header MSVC finds next to an includer; Linux doesn't), and Tracktion's names (`te::`) in each model area, the app, the services and the tests (`tracktion-<area>`: the migration off Tracktion only lowers them), and compares each count with `tools/architecture-budget.txt`. CI's Checks job and pre-commit check 7 run it; pre-push checks raises. Run `sh tools/check-architecture.sh` (Bash tool) after changing `src/`, `tests/` or `CMakeLists.txt`. When a change removes matches, run `--update` and commit the lower budget with it; when it adds matches, change the code instead (`--list <rule>` shows each match). Raise a budget only when a plan step moves code between layers on purpose: put `Architecture-Budget-Raise: <rule> <old> -> <new>: <reason>` in the commit message (CI and pre-push check it; keep it when squashing) and commit with `git -c phazite.allowBudgetIncrease=true commit -F <file>`; otherwise ask the user.

## Code conventions

- Every C/C++ file starts with `// SPDX-License-Identifier: AGPL-3.0-or-later`.
- C++20. Include JUCE's module headers directly (`<juce_gui_basics/juce_gui_basics.h>`), not `JuceHeader.h`. Model and services code gets Tracktion from `src/model/base/internal/Tracktion.h`, which includes `<tracktion_engine/tracktion_engine.h>` and declares `namespace te = tracktion;`. Qualify `juce::`.
- Create and destroy Tracktion objects (Engine, Edit) on the message thread, and destroy every `te::Edit` before the `te::Engine`.
- Every user action is a command in `phazite::CommandRegistry` (`src/model/commands/CommandRegistry.h`, which has no UI code; menus, keys and the shortcuts editor reach it through `ui::CommandBridge` and `ui::KeyDispatcher` in `src/ui/input/`). Give it a stable id (`category.action`, e.g. `edit.undo`), a name, a one-sentence description and search synonyms. Set `undoTarget` to the song's undo history if it changes a project (`undoTargetOf()` in `src/model/commands/internal/Undo.h`, or the context's `getUndoManager()`), so it becomes one named undo step. Menus, shortcuts and the command palette use the registry; default shortcuts belong in the keymaps in `resources/keymaps/` (JUCE key descriptions, "command" for Ctrl/Cmd), not in code. While the computer keyboard plays notes, Shift and a letter run that letter's single-key shortcut (the owner's decision, as in Ableton Live), so a keymap must not give Shift and a letter a different command than the letter alone. When commands share a key, the enabled one with the highest `keyPriority` runs: note commands use `Command::notePriority`, so the arrow keys move selected notes and otherwise select tracks. A held key runs its command once; set `repeatsWhileHeld` on commands that take a step (nudging, zooming, transposing, moving through tracks, undo) so that they repeat while it is held. Set `overPlugins` on a command whose key should work while a plug-in window has the keyboard focus (play and stop do). The time line's commands (zoom, grid, tools, nudge, quantize) act on the editor used last (`addTimelineCommands()` in `src/ui/timeline/TimelineEditor.h`).
- Keep registrations declarative: a command's perform, isEnabled, isTicked and currentName each call one named function from the area's header, which a test calls directly; with the Edit, through `withEdit()`/`ifEdit()` (`src/model/commands/internal/Undo.h`). Don't hide logic in registration lambdas or in anonymous-namespace helpers behind them. A switch for several things uses `toggleAll()`/`areAllOn()` (`src/model/base/Toggles.h`). The command goldens (`tests/golden/commands/`) record the catalogue and each command's states: change them on purpose, together with the command.
- Undo and redo with `phazite::undo()` and `redo()` (`src/model/commands/internal/Undo.h`), never `te::Edit::undo()`: they take a step in the song's history, and the mirror then brings Tracktion's Edit in line with the song (`mirror::reconcileAll()`).
- The open project is the `ProjectContext` (`src/model/project/ProjectContext.h`) that `ProjectSession` owns: its Edit, what is selected in it (one `phazite::Selection`, `src/model/base/internal/Selection.h`, which Phazite holds by IDs in place of Tracktion's selection manager, and which views reach by IDs: `getSongSelection()`, notes by their references among the clips the piano roll shows) and the time range selected across tracks (by beats and IDs: `getSongRange()`). Only `ProjectSession` changes which Edit it holds. Views listen to it (`ProjectContext::Listener`): for another project, and for what changed in the song, in groups (`SongChanges`), once a turn of the message loop. They name what they show by ID and forget it when another project opens, whose items can have the same IDs (the app closes menus then, as theirs capture IDs); `getProjectNumber()` tells them another project from the same one again. Its header has no Tracktion: model and app code that holds the context finds the open Edit with `getEdit (context)`, the selection with `getSelection (context)` and the range with `getRangeSelection (context)` (`src/model/project/internal/ProjectContext.h`, which also has the session's `setEdit()`); model commands that act on the selection take the `Selection` (as `addTrackCommands()` in `src/model/arrangement/internal/Tracks.h` does) and use `selection.getEdit()`, the same Edit. Tracktion functions that would select what they make are given no selection manager: the model selects it in the `Selection` itself. Never read `UIBehaviour`'s focused Edit (kept in step for Tracktion), and don't pass Edit getters around.
- Create the Engine only with `phazite::createEngine()` (`src/model/engine/internal/EngineSetup.h`), never `te::Engine` directly: Tracktion's default settings storage writes the user's full name into every saved project. Open saved projects with `Project::open()`: a project file is the song alone, which `createEditFromSong()` builds an Edit from, on the message thread (never Tracktion's `EditLoader` or `loadEditFromFile()`).
- Store what devices hold of their state outside the project (a plug-in's own settings, where its window was) with `phazite::storeDeviceState()` or `storeDeviceStates()` (`src/model/devices/internal/DeviceStates.h`), never Tracktion's `Edit::flushState()`, `flushPluginStateToValueTree()` or `flushPluginStateIfNeeded()`, which write it through the undo manager; before the song copies a track, `Song::storeDeviceStates()` stores its devices' (`src/model/base/Song.h`). `Project` writes the song alone into its files, never Tracktion's Edit (nor with `EditFileOperations`).
- The song's end is `phazite::getSongEnd()` (`src/model/transport/internal/Playback.h`): the end of the bar its last clip ends in. Not `te::Edit::getLength()`, which counts Tracktion's clips but none of what Phazite keeps itself; the playlist's scrolling and Zoom to Fit use `getTimelineEnd()` (`src/model/arrangement/PlaylistModel.h`), which counts the sections and the chord lane too, on purpose (the previewer uses `te::Edit::getLength()` for the small Edit each sound plays in).
- Keep the build warning-free under JUCE's recommended warning flags (/W4 on MSVC). Don't silence a warning without saying why.
- Formatting comes from `.clang-format` (JUCE style). After editing C/C++ files, run `sh tools/format.sh` with the Bash tool (on Windows it uses the clang-format 23 bundled with VS Code's C/C++ extension), and check with `sh tools/format.sh --check`. Don't hand-align code or trailing comments that the formatter will undo; use `// clang-format off` / `// clang-format on` only where a hand layout carries meaning (such as a table).

## Committing

The repository will be public on GitHub, and a commit stays in its history even after a later commit deletes the file. The user's rule: nothing confidential may ever reach the remote. Before every commit:
- Read `git diff --cached` in full and check that nothing confidential is staged: API keys and tokens (including AI providers'), passwords, private keys, signing certificates, `.env` files, crash dumps, and personal data such as email addresses or local paths containing user names. If anything looks sensitive, stop and ask the user.
- Secrets never go in tracked files, including `.vscode/launch.json`, `CMakePresets.json` and `.claude/settings.json`. Keep them in environment variables or in files git ignores (`.env`, `CMakeUserPresets.json`, `.claude/settings.local.json`).
- The git hooks (`.githooks/`) also stop a commit, merge or push whose email isn't a GitHub noreply address, or whose changes or messages gitleaks flags. They don't replace reading the diff. Never skip them with `--no-verify` (commit or push), never change `core.hooksPath`, and never use `-c phazite.allowPublicEmail=true` unless the user asks; if a hook stops something, show the user its message and ask how to proceed. For a false positive the user has checked, add `gitleaks:allow` to that line, or add the printed `Fingerprint` line to `.gitleaksignore` where comments aren't possible.
- The pre-commit hook also refuses changed dependency pins (`external/`, `.gitmodules`), staged files over 5 MiB, trailing whitespace, leftover conflict markers, unformatted C/C++ and code that doesn't match the architecture budgets. Fix the cause; use `-c phazite.allowSubmoduleBump=true` only for a deliberate bump, `-c phazite.allowLargeFiles=true` only when the user asks, and `-c phazite.allowBudgetIncrease=true` only as "Architecture rules" says.
- Stage a new or changed hook with `git add --chmod=+x .githooks/<name>`: Windows records no executable bit, and git on Linux and macOS silently skips a hook without it. `git ls-files -s .githooks` must show mode 100755.
- In WSL/Linux the hooks need gitleaks 8.19 or newer from its GitHub releases (Ubuntu's own package is 8.16) and `git config core.hooksPath .githooks` once per clone.
- Commit messages: write them to a file and use `git commit -F <file>`. Windows PowerShell 5.1 splits a `-m` argument at embedded double quotes.
- Never add a remote or push unless the user asks.
