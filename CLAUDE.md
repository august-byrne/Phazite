# Phazite

Open-source DAW (AGPL-3.0-or-later) in C++20 on JUCE, with its own song model, playback engine and plug-in hosting. It hosts VST3 plug-ins (AU on macOS later). Performance and low resource use matter in both the audio engine and the UI.

## Build

Run every command from the repository root. The presets are the only entry point, and the same two commands work on every OS.

- `cmake --list-presets` shows the presets for this machine: `windows-debug`, `windows-profile` (Release with symbols: for playing, profiling and the benchmarks), `windows-release` on Windows; `linux-debug`, `linux-release`, `linux-asan`, `linux-tsan` on Linux/WSL.
- Configure: `cmake --preset <preset>`. Build: `cmake --build --preset <preset>`. Test: `ctest --preset <preset>`, after a build of the same preset (it runs `phazite_tests` once for each test file, named after it, 4 at once, each with a temporary folder of its own; all passed when it prints `100% tests passed` and exits 0; `-R <name>` runs some files only, `-j <n>` more at once). To run some tests only, call the test executable directly, for example `build\windows-debug\phazite_tests_artefacts\Debug\phazite_tests.exe --test-case="*save*"`.
- Installer (Windows): `cmake --build --preset windows-release --target installer` builds the app, then `build\windows-release\installer\Phazite-<version>-Setup.exe` with Inno Setup 6.6 or newer (the setup script installs it), with its SHA-256 (`.sha256`) and the update file a release carries (`phazite-update.json`) beside it. `tools\test-installer.ps1 <installer>` installs it for this user, silently, checks it and uninstalls it; it changes this PC's registry and Start menu meanwhile, so ask the user before running it.
- Run configure and build as separate commands, each with run_in_background and without redirections or pipes (no `>`, `*>`, `2>&1`, `Tee-Object`): the complete output lands in the task's output file. When a command finishes, check its exit code and search that file case-insensitively for `error` and `warning` (this also catches "CMake Warning"), plus `D9` and `LNK4`. The first configure of a build folder also builds JUCE's `juceaide` helper (1-2 minutes); a full build takes several minutes.
- On Windows the shell is Windows PowerShell 5.1: there is no `&&`/`||`, and `;` does not stop after a failure. Use separate commands, or `A; if ($LASTEXITCODE -eq 0) { B }`. In WSL/Linux the shell is Bash.
- Never run vcvars/VsDevCmd, open a Developer PowerShell, or call `cl`, `link`, `msbuild` or `ninja` directly. MSVC is found by `cmake/toolchains/windows-msvc.cmake`, which wraps `external/WindowsToolchain`.
- After a Visual Studio Build Tools update (new MSVC version) or a toolchain change, reconfigure with `cmake --preset <preset> --fresh`. If that folder still fails, delete `build\<preset>` and configure again.
- Before configuring or building, run `@(Get-Process -Name cmake, ninja -ErrorAction Ignore).Count`. If it prints anything other than 0 and you didn't start those processes (VS Code may be building), ask the user before continuing: two builds in one folder break each other.

## Tools (Windows)

- `tools\setup-windows.cmd` installs or updates every tool (including gitleaks and Inno Setup) and turns on this clone's git hooks (`core.hooksPath = .githooks`). A full run needs the user at a UAC prompt and can take up to an hour (a few minutes when everything is current), so start it only when the user asks (as a background command) or ask them to run it. `tools\setup-windows.cmd -CheckOnly` is safe at any time: no admin rights, changes nothing.
- Exit codes (your shell tool shows 3010 as 194; the script's last line, "Result: ...", always states it): 0 = done; 3010 = done, but Windows must restart (ask the user to reboot, then run it again); 1 = a step failed (read the FAILED lines and the log path it prints); 2 = it could not start. With `-CheckOnly`: 0 = all present, 1 = something missing (including this clone's git hooks) or not on this shell's PATH, 3010 = Visual Studio is waiting for a reboot. Switches: `-CheckOnly`, `-SkipUpdates`, `-WithTestPlugin` (Surge XT), `-WithLlvm`, `-SkipVSCodeExtensions`.
- If `cmake` or `git` is "not recognized", run `tools\setup-windows.cmd -CheckOnly`. If it finds the tools, the program that started Claude Code has an old PATH: ask the user to quit every VS Code window, start VS Code from the Start menu and close any terminals it restores (or to open a new terminal and start Claude there). If it reports MISSING, ask the user to run the setup. Don't edit PATH or search the disk for tools. If it prints `hooks ... OFF`, the git hooks are off in this clone: tell the user, then run `git config core.hooksPath .githooks` (no admin rights or full setup needed).

## Running and debugging

- The app is `build/<preset>/Phazite_artefacts/<build type>/Phazite` (`.exe` on Windows), where the build type is `Debug` for `*-debug` and `linux-asan`, `Release` for `*-release`, and `RelWithDebInfo` for `windows-profile` and `linux-tsan`; its helper program, `PhaziteHost`, which hosts the plug-ins, is copied next to it after each build. Run the TSan build as `TSAN_OPTIONS=suppressions=tools/tsan-suppressions.txt setarch $(uname -m) -R build/linux-tsan/Phazite_artefacts/RelWithDebInfo/Phazite`. That file is for known races in code Phazite can't change (JUCE's), each explained there and in `docs/realtime-audit.md`, and the linux-asan tests' `tools/lsan-suppressions.txt` the same for known leaks; both are empty now. A race or a leak in Phazite's own code is fixed, never suppressed.
- The app is for the user to run, or to start with F5 in VS Code. Don't start it from the shell unless asked; then use `Start-Process <path>` (a bare call blocks the tool until the window closes). Tell the user what to click and listen for.
- Debugging: VS Code's "Phazite (Windows)" launch configuration (F5) builds the active preset and starts the app under the debugger. A crash outside a debugger leaves a dump in `%LOCALAPPDATA%\CrashDumps\Phazite.exe.*.dmp`; open it with the "Open crash dump (Windows, Debug build)" configuration. Only `windows-debug` and `windows-profile` builds have symbols, so reproduce Release crashes in one of those.
- VS Code configures only on request. After a build folder was created from the shell (first configure, or after deleting `build\<preset>`), ask the user to run "CMake: Configure" once in VS Code so IntelliSense and F5 know about it.
- LNK1104 on Phazite.exe means the app or a debug session is still running: ask the user to close it.

## Real-time rules (audio thread)

The audio thread is the audio callback and everything it calls: Phazite's engine playing a block (`engine::Engine::process()`, with its worker threads, and every device's and plug-in's `process`), a helper's thread that plays a plug-in's blocks (`src/host/core/Instance.h`), and any helper reached from them. On the audio thread:
- No memory allocation or release: no `new`/`delete`/`malloc`, no growing `std::vector`/`juce::Array`, no creating `std::string`/`juce::String`, no allocating `std::function` captures. Allocate up front when preparing.
- No locks or waiting: no `std::mutex`, `juce::CriticalSection`/`ScopedLock`, condition variables, `WaitableEvent`, `MessageManagerLock`, or blocking calls into other threads.
- No posting to the message thread: no `triggerAsyncUpdate`, `sendChangeMessage` or `juce::MessageManager::callAsync` (they lock or allocate). Set an atomic flag instead and poll it from a `juce::Timer`.
- No file or network I/O, no logging (`DBG`, `juce::Logger`, `std::cout`), no system calls that can block.
- No throwing exceptions, no unbounded loops.
- Threads communicate through lock-free queues (FIFOs such as `juce::AbstractFifo`, or the engine's `engine::EventQueue`, `src/engine/core/EventQueue.h`, for several threads into one) and lock-free `std::atomic` values (add `static_assert (std::atomic<T>::is_always_lock_free)` for anything wider than a pointer), not shared mutable state; what the audio thread plays is handed to it whole and freed on the message thread (`src/engine/core/Handover.h`).
- Read parameters on the audio thread from what the engine holds of them (a device's values set by hand in `engine::DeviceNode`, atomics the message thread sets, and the plan's automation curves), never through `juce::ValueTree`, `juce::CachedValue` or other message-thread objects.
- The device list (`phazite::getDeviceTypes()`) offers Phazite's own devices and the plug-ins found by scanning, which play in helper processes. Phazite's devices follow these rules, and each has a guarded scenario in the real-time audit.
- `docs/realtime-audit.md` lists what is known to break these rules (in JUCE's code, or a plug-in's in its helper) and what Phazite does about each. After changes that touch playback, run the audit (`phazite_tests.exe --test-suite=realtime-audit` from the `windows-debug` build): it counts allocations on the audio thread and shows where they come from. Its guarded scenarios fail if steady playback allocates.

## Architecture rules

The code is layered so that the UI can change without touching the rules of editing, every edit can be tested without a window, and parts of the engine could be replaced later (`docs/design.md`, section 24). The roadmap's architecture track (phases A0 to A6) moves the existing code there; new code follows these rules now.
- Dependencies point down: `src/app/` may include `ui/`, `services/` and `model/`; `src/ui/` may include `services/` and `model/`; `src/services/` may include `model/`; `src/model/` includes none of them, but `engine/`, Phazite's playback engine, which includes only `devices/`, and `sandbox/`, what Phazite shares with the helpers that host plug-ins, which includes only `devices/` too. `src/host/`, the helper program, includes `sandbox/` and `devices/`, and no layer includes it. Every layer may include `devices/`, which includes none of the others. Tests and tools may include anything.
- No window code below the UI: `src/model/`, `src/services/`, `src/engine/`, `src/sandbox/` and `src/devices/` include no JUCE window module (`juce_gui_basics`, `juce_gui_extra`) and name no window class (`juce::Component`, `juce::KeyPress`...); `juce_graphics`, for `juce::Colour` values, is allowed in the model and services for now. Key and mouse handling, pixel sizes and how values are shown belong in `src/ui/`.
- Devices, the engine and the sandbox are engine-neutral: `src/devices/`, `src/engine/`, `src/sandbox/` and the helper program, `src/host/`, know nothing of the song model or the layers above. Phazite's engine plays a device through `engine::DeviceRunner` and `DeviceNode` (`src/engine/nodes/`), which hand it the audio, the notes and its parameters' values; the model compiles the song into what the engine plays (`src/model/playback/internal/SongPlayer.h`).
- The UI decides nothing about the project: UI code doesn't start undo steps or change the project; it runs a command or calls a model function, and a control changes a parameter through a `ParameterHandle`. Phase A2 moved the UI's undo steps and edits into the model.
- The model's insides stay in the model: `src/ui/` includes no model `internal/` header (those take the song, its elements or what plays it), and doesn't reach them through `auto` or aliases either. Call a model function that takes and returns Phazite's own types (IDs, plain values, handles), and add one, with a test, if there is none. A model header that takes the song or its elements goes in its area's `internal/` folder; the model's other headers stay what the UI may use.
- Every change to a project is one named undo step with one owner: a command (through `undoTarget`; the registry opens the step), or a model function that is a change of its own (its comment says so, as `addDeviceTo()`'s does), which begins with `phazite::UndoStep` (`src/model/commands/internal/Undo.h`). Other model functions make their changes through the song's undo history (`Song::getUndoManager()`, `src/model/base/Song.h`) and never begin a step, so their changes join the caller's step; an `UndoStep` begun inside another for the same song joins it. A change that spans several events, such as a drag, is a `phazite::Gesture` (`Undo.h`): one named step from its start to its commit, which `UndoStep`s begun meanwhile join, or rolled back (`rollBack()`, meant for Escape during a drag, which no tool handles yet) leaving nothing to redo. View state is written without an undo manager. A command that moves the selected time range to what it made moves it with `RangeSelection::setInUndoStep()`, so that Undo puts it back; a range selected by hand isn't an undo step. What a new project starts with is added through `Project::create()`'s content function, which goes into its first save, so it is neither an undo step nor an unsaved change. Changes that are deliberately not undo steps (mute and solo, freezing a track, the loop, view state) are model functions too.
- View state (track heights, collapsed and pinned tracks, drum mode and drum rows, both editors' grid settings, where a device's window was) is saved, but written without an undo step and doesn't count as an unsaved change (decision 4). Two lists say what it is, and must stay exact: `schema::isTrackViewProperty()`, `isGridProperty()`, `isDeviceViewProperty()` and the PIANOROLL element in `Schema.h`, and `schema::isUncountedProperty()` / `isUncountedElement()` there, which use them for the project's notifications and its comparison with the saved copy, and for the versions' differences, alike.
- Every name Phazite writes into a project file is defined once, in `src/model/base/internal/Schema.h`, with where it is stored and what it holds; read and write the song's data only through those names and the song (`Song::getState()`). A device's type and parameter IDs, in its description in `src/devices/`, are saved too (`Schema.h` says how; a choice's value is saved as its number). Save Phazite's own values (names or Phazite's enums), never a library's enum number.
- No backward compatibility while Phazite is pre-alpha (the owner's decision, 2026-10-18; `docs/design.md`, section 18): projects, presets and settings saved by an earlier build needn't open or keep what they held. So there are no format versions or migrations, and no code, tests or comments kept for what earlier builds saved or played; remove such leftovers as you find them. Rename or reorder anything saved (names in `Schema.h`, device and parameter IDs, a choice's order, settings keys) when that makes the code clearer, regenerate the golden files, and say why in the commit message. The owner will say when compatibility starts; until then, don't add version checks or upgrade paths.
- Phazite's own settings (the `phazite*` keys) are read and written only through `phazite::Settings` (`src/services/Settings.h`), which lists every key once with its default and when it is saved; a new setting goes into that list.
- Every colour, size, corner radius and font in the UI comes from the design tokens (`DesignTokens.h`, read with `ui::getPalette (component)`); if none fits, add a token rather than a literal. A colour a component sets on itself or a child (`setColour()`) straight from the palette goes through `ui::setThemeColour()` (`src/ui/theme/LookAndFeel.h`), which a theme switch (`ui::refreshTheme()`) sets again; one it works out from its state (an attention tint, a track's ink) it sets again in its `lookAndFeelChanged()`. Phase A4 moves the tokens into a file a designer edits, with a gallery app, and the text the user reads into a strings table.
- Meters, the playhead and other values that change many times a second are read from small read-only sources polled by the displays' ticker (`ui::DisplayTicker`), a `juce::Timer` or, for the playhead while playing, the display's frames (`juce::VBlankAttachment`), never stored in the project or sent as change messages. A display repaints only when what it draws moved (`ui::DrawnNumbers`): in silence, with nothing turned, nothing repaints. A component that paints all of itself in opaque colours says so (`setOpaque (true)`), so that what is behind it doesn't repaint with it; and a view of many items (the playlist's clips) makes components only for those in view.
- `tools/check-architecture.sh` counts what these rules forbid: includes that point up a layer (`upward-includes`); JUCE window modules and window classes in the model, the services, the engine, the sandbox and the devices (`model-window-includes`, `model-window-references`); undo steps begun in the model or the services outside the undo code (`model-undo-steps`) and in the UI or the app (`ui-undo-steps`); model and services files on include loops (`model-include-loops`); the model's `internal/` headers included in the UI (`ui-internal-includes`); C/C++ files directly in `src/model/`, `src/ui/`, `src/engine/`, `src/sandbox/`, `src/host/` or `src/devices/` (`flat-files`); `#include "..."` lines in `src/`, `tests/` and `tools/` that name no file exactly (`unresolved-includes`), and source paths in `CMakeLists.txt` that name no file exactly or C/C++ files it doesn't list (`cmake-sources`; Windows forgives a wrong case or a header MSVC finds next to an includer; Linux doesn't); and an include or a name of Tracktion Engine anywhere in `src/`, `tests/` or `tools/` (`tracktion`: Phazite builds on JUCE alone). It compares each count with `tools/architecture-budget.txt`, where every budget is 0. CI's Checks job and pre-commit check 7 run it; pre-push checks raises. Run `sh tools/check-architecture.sh` (Bash tool) after changing `src/`, `tests/` or `CMakeLists.txt`. When a change removes matches, run `--update` and commit the lower budget with it; when it adds matches, change the code instead (`--list <rule>` shows each match). Raise a budget only when a plan step moves code between layers on purpose: put `Architecture-Budget-Raise: <rule> <old> -> <new>: <reason>` in the commit message (CI and pre-push check it; keep it when squashing) and commit with `git -c phazite.allowBudgetIncrease=true commit -F <file>`; otherwise ask the user.

## Code conventions

- Every C/C++ file starts with `// SPDX-License-Identifier: AGPL-3.0-or-later`.
- C++20. Include JUCE's module headers directly (`<juce_gui_basics/juce_gui_basics.h>`), not `JuceHeader.h`. Qualify `juce::`.
- Create and destroy songs, projects, project contexts and the engine context on the message thread, and destroy every project context before the engine context it plays on.
- Every user action is a command in `phazite::CommandRegistry` (`src/model/commands/CommandRegistry.h`, which has no UI code; menus, keys and the shortcuts editor reach it through `ui::CommandBridge` and `ui::KeyDispatcher` in `src/ui/input/`). Give it a stable id (`category.action`, e.g. `edit.undo`), a name, a one-sentence description and search synonyms. Set `undoTarget` to the song's undo history if it changes a project (`undoTargetOf()` in `src/model/commands/internal/Undo.h`, or the context's `getUndoManager()`), so it becomes one named undo step. Menus, shortcuts and the command palette use the registry; default shortcuts belong in the keymaps in `resources/keymaps/` (JUCE key descriptions, "command" for Ctrl/Cmd), not in code. While the computer keyboard plays notes, Shift and a letter run that letter's single-key shortcut (the owner's decision, as in Ableton Live), so a keymap must not give Shift and a letter a different command than the letter alone. When commands share a key, the enabled one with the highest `keyPriority` runs: note commands use `Command::notePriority`, so the arrow keys move selected notes and otherwise select tracks. A held key runs its command once; set `repeatsWhileHeld` on commands that take a step (nudging, zooming, transposing, moving through tracks, undo) so that they repeat while it is held. Set `overPlugins` on a command whose key should work while a plug-in window has the keyboard focus (play and stop do). The time line's commands (zoom, grid, tools, nudge, quantize) act on the editor used last (`addTimelineCommands()` in `src/ui/timeline/TimelineEditor.h`).
- Keep registrations declarative: a command's perform, isEnabled, isTicked and currentName each call one named function from the area's header, which a test calls directly; with the song, through `withSong()`/`ifSong()` (`src/model/commands/internal/Undo.h`). Don't hide logic in registration lambdas or in anonymous-namespace helpers behind them. A switch for several things uses `toggleAll()`/`areAllOn()` (`src/model/base/Toggles.h`). The command goldens (`tests/golden/commands/`) record the catalogue and each command's states: change them on purpose, together with the command.
- Undo and redo with `phazite::undo()` and `redo()` (`src/model/commands/internal/Undo.h`): a step in the song's history, which what plays follows (the song's playback session hears the song change), the values set by hand included.
- The open project is the `ProjectContext` (`src/model/project/ProjectContext.h`) that `ProjectSession` owns: its song (which its `Project` owns), what is selected in it (one `phazite::Selection`, `src/model/base/internal/Selection.h`, held by IDs, which views reach by IDs: `getSongSelection()`, notes by their references among the clips the piano roll shows), the time range selected across tracks (by beats and IDs: `getSongRange()`), and the song's playback session, its clip renders, its clipboard and what remembers the parameter touched last. Only `ProjectSession` (and tests) changes which song it holds. Views listen to it (`ProjectContext::Listener`): for another project, and for what changed in the song, in groups (`SongChanges`), once a turn of the message loop. They name what they show by ID and forget it when another project opens, whose items can have the same IDs (the app closes menus then, as theirs capture IDs); `getProjectNumber()` tells them another project from the same one again. Its header has none of the model's insides: model and app code that holds the context finds the open song with `findSong (context)`, the selection with `getSelection (context)`, the range with `getRangeSelection (context)` and the playback session with `getSession (context)` (`src/model/project/internal/ProjectContext.h`, which also has the session's `setSong()`); model commands that act on the selection take the `Selection` (as `addTrackCommands()` in `src/model/arrangement/internal/Tracks.h` does) and use `selection.getSong()`, the same song. Model functions that make something select it in the `Selection` themselves; don't pass song getters around.
- Make the engine context once, with `phazite::createEngineContext()` (`src/model/engine/internal/EngineContext.h`): the app's as it starts, which outlives every project context, and the tests' one for all of them. Open saved projects with `Project::open()`: a project file is the song alone, which `makeSong()` (`src/model/project/internal/Project.h`) makes a `Song` of, with what every song has added, on the message thread.
- What devices hold of their state outside the song's undo history (a plug-in's own settings, program and channel layout) is stored into the song with `Song::storeDeviceStates()` (`src/model/base/Song.h`), before the song is saved and before it copies a track or a device; the song's plug-ins' instances set the store (`src/model/plugins/internal/PluginInstances.h`), and a change a plug-in makes in its own window counts as an unsaved change (`Song::markChangedOutsideHistory()`). `Project` writes the song alone into its files.
- The song's end is `phazite::getSongEnd()` (`src/model/transport/internal/Playback.h`): the end of the bar its last clip ends in. The playlist's scrolling and Zoom to Fit use `getTimelineEnd()` (`src/model/arrangement/PlaylistModel.h`), which counts the sections and the chord lane too, on purpose.
- Keep the build warning-free under JUCE's recommended warning flags (/W4 on MSVC). Don't silence a warning without saying why.
- Formatting comes from `.clang-format` (JUCE style). After editing C/C++ files, run `sh tools/format.sh` with the Bash tool (on Windows it uses the clang-format 23 bundled with VS Code's C/C++ extension), and check with `sh tools/format.sh --check`. Don't hand-align code or trailing comments that the formatter will undo; use `// clang-format off` / `// clang-format on` only where a hand layout carries meaning (such as a table).

## Committing

The repository will be public on GitHub, and a commit stays in its history even after a later commit deletes the file. The user's rule: nothing confidential may ever reach the remote. Before every commit:
- Read `git diff --cached` in full and check that nothing confidential is staged: API keys and tokens (including AI providers'), passwords, private keys, signing certificates, `.env` files, crash dumps, and personal data such as email addresses or local paths containing user names. If anything looks sensitive, stop and ask the user.
- Secrets never go in tracked files, including `.vscode/launch.json`, `CMakePresets.json` and `.claude/settings.json`. Keep them in environment variables or in files git ignores (`.env`, `CMakeUserPresets.json`, `.claude/settings.local.json`).
- The git hooks (`.githooks/`) also stop a commit, merge or push whose email isn't a GitHub noreply address, or whose changes or messages gitleaks flags. They don't replace reading the diff. Never skip them with `--no-verify` (commit or push), never change `core.hooksPath`, and never use `-c phazite.allowPublicEmail=true` unless the user asks; if a hook stops something, show the user its message and ask how to proceed. For a false positive the user has checked, add `gitleaks:allow` to that line, or add the printed `Fingerprint` line to `.gitleaksignore` where comments aren't possible.
- The pre-commit hook also refuses changed dependency pins (`external/`, `.gitmodules`), staged files over 5 MiB, trailing whitespace, leftover conflict markers, unformatted C/C++ and code that doesn't match the architecture budgets. Fix the cause; use `-c phazite.allowSubmoduleBump=true` only for a deliberate bump, `-c phazite.allowLargeFiles=true` only when the user asks, and `-c phazite.allowBudgetIncrease=true` only as "Architecture rules" says.
- Stage a new or changed hook with `git add --chmod=+x .githooks/<name>`: Windows records no executable bit, and git on Linux and macOS silently skips a hook without it. `git ls-files -s .githooks` must show mode 100755.
- In WSL/Linux the hooks need gitleaks 8.19 or newer from its GitHub releases (Ubuntu's own package is 8.16) and `git config core.hooksPath .githooks` once per clone.
- Commit messages: write them to a file and use `git commit -F <file>`. Windows PowerShell 5.1 splits a `-m` argument at embedded double quotes.
- Never add a remote or push unless the user asks.
