# Phazite

Open-source DAW (AGPL-3.0-or-later) in C++20 on JUCE, with its own song model, playback engine and plug-in hosting. It hosts VST3 plug-ins (AU on macOS later). Performance and low resource use matter in both the audio engine and the UI.

## Build

Run every command from the repository root. The presets are the only entry point, and the same two commands work on every OS.

- `cmake --list-presets` shows the presets for this machine: `windows-debug`, `windows-profile` (Release with symbols: for playing, profiling and the benchmarks), `windows-release`, `windows-asan` (Debug with AddressSanitizer, which needs Visual Studio's x64 ASan component: the setup script installs it) on Windows; `linux-debug`, `linux-release`, `linux-asan`, `linux-tsan`, `linux-clang` (Clang, for `tools/clang-tidy.sh`) on Linux/WSL.
- Configure: `cmake --preset <preset>`. Build: `cmake --build --preset <preset>`. Test: `ctest --preset <preset>`, after a build of the same preset (it runs `phazite_tests` once for each test file, named after it, 4 at once, each with a temporary folder of its own, and starts the app itself once in its smoke test, `Phazite --smoke-test` (`PhaziteStarts`), which needs the whole preset built, not `phazite_tests` alone; all passed when it prints `100% tests passed` and exits 0; `-R <name>` runs some files only, `-j <n>` more at once). To run some tests only, call the test executable directly, for example `build\windows-debug\phazite_tests_artefacts\Debug\phazite_tests.exe --test-case="*save*"`.
- Installer (Windows): `cmake --build --preset windows-release --target installer` builds the app, then `build\windows-release\installer\Phazite-<version>-Setup.exe` with Inno Setup 6.6 or newer (the setup script installs it), with its SHA-256 (`.sha256`) and the update file a release carries (`phazite-update.json`) beside it. `tools\test-installer.ps1 <installer>` installs it for this user, silently, checks it and uninstalls it; it changes this PC's registry and Start menu meanwhile, so ask the user before running it.
- JUCE's module headers are precompiled for Phazite's own files (`PHAZITE_PRECOMPILED_HEADERS`, on by default: a full build is about five times faster). CI builds with it off, where ccache can't use them, so a file that compiles here only because of the precompiled header fails there: every file includes what it uses. The folder beside the app (`fonts/`, `presets/`, `licenses/`, `PhaziteHost`, `NOTICES.txt`) is made the same as its sources at every build of the app (`cmake/SyncAppFolder.cmake`).
- Run configure and build as separate commands, each with run_in_background and without redirections or pipes (no `>`, `*>`, `2>&1`, `Tee-Object`): the complete output lands in the task's output file. When a command finishes, check its exit code and search that file case-insensitively for `error` and `warning` (this also catches "CMake Warning"), plus `D9` and `LNK4`. The first configure of a build folder also builds JUCE's `juceaide` helper (1-2 minutes); a full build takes several minutes.
- On Windows the shell is Windows PowerShell 5.1: there is no `&&`/`||`, and `;` does not stop after a failure. Use separate commands, or `A; if ($LASTEXITCODE -eq 0) { B }`. In WSL/Linux the shell is Bash.
- Never run vcvars/VsDevCmd, open a Developer PowerShell, or call `cl`, `link`, `msbuild` or `ninja` directly. MSVC is found by `cmake/toolchains/windows-msvc.cmake`, which wraps `external/WindowsToolchain`.
- After a Visual Studio Build Tools update (new MSVC version) or a toolchain change, reconfigure with `cmake --preset <preset> --fresh`. If that folder still fails, delete `build\<preset>` and configure again.
- Before configuring or building, run `@(Get-Process -Name cmake, ninja -ErrorAction Ignore).Count`. If it prints anything other than 0 and you didn't start those processes (VS Code may be building), ask the user before continuing: two builds in one folder break each other.

## Tools (Windows)

- `tools\setup-windows.cmd` installs or updates every tool (including gitleaks and Inno Setup) and turns on this clone's git hooks (`core.hooksPath = .githooks`). A full run needs the user at a UAC prompt and can take up to an hour (a few minutes when everything is current), so start it only when the user asks (as a background command) or ask them to run it. `tools\setup-windows.cmd -CheckOnly` is safe at any time: no admin rights, changes nothing.
- Exit codes (your shell tool shows 3010 as 194; the script's last line, "Result: ...", always states it): 0 = done; 3010 = done, but Windows must restart (ask the user to reboot, then run it again); 1 = a step failed (read the FAILED lines and the log path it prints); 2 = it could not start. With `-CheckOnly`: 0 = all present, 1 = something missing (including this clone's git hooks) or not on this shell's PATH, 3010 = Visual Studio is waiting for a reboot. Switches: `-CheckOnly`, `-SkipUpdates`, `-WithTestPlugin` (Surge XT), `-WithLlvm`, `-SkipVSCodeExtensions`.
- If `cmake` or `git` is "not recognized", run `tools\setup-windows.cmd -CheckOnly`. If it finds the tools, the program that started Claude Code has an old PATH: ask the user to quit every VS Code window, start VS Code from the Start menu and close any terminals it restores (or to open a new terminal and start Claude there). If it reports MISSING, ask the user to run the setup. Don't edit PATH or search the disk for tools. If it prints `hooks ... OFF`, the git hooks are off in this clone: tell the user, then run `git config core.hooksPath .githooks` (no admin rights or full setup needed).

## Running and debugging

- The app is `build/<preset>/Phazite_artefacts/<build type>/Phazite` (`.exe` on Windows), where the build type is `Debug` for `*-debug` and `linux-asan`, `Release` for `*-release`, and `RelWithDebInfo` for `windows-profile` and `linux-tsan`; its helper program, `PhaziteHost`, which hosts the plug-ins, is copied next to it after each build. Run the TSan build as `TSAN_OPTIONS=suppressions=tools/tsan-suppressions.txt setarch $(uname -m) -R build/linux-tsan/Phazite_artefacts/RelWithDebInfo/Phazite`. That file is for known races in code Phazite can't change (JUCE's), each explained there and in `docs/realtime-audit.md`, and the linux-asan tests' `tools/lsan-suppressions.txt` the same for known leaks; both are empty now. A race or a leak in Phazite's own code is fixed, never suppressed.
- The app is for the user to run, or to start with F5 in VS Code. Don't start it from the shell unless asked; then use `Start-Process <path>` (a bare call blocks the tool until the window closes). Tell the user what to click and listen for.
- Debugging: VS Code's "Phazite (Windows)" launch configuration (F5) builds the active preset and starts the app under the debugger. A crash outside a debugger leaves a dump in `%LOCALAPPDATA%\CrashDumps\Phazite.exe.*.dmp`; open it with the "Open crash dump (Windows, Debug build)" configuration. Only `windows-debug` and `windows-profile` builds have symbols, so reproduce Release crashes in one of those.
- VS Code configures only on request. After a build folder was created from the shell (first configure, or after deleting `build\<preset>`), ask the user to run "CMake: Configure" once in VS Code so IntelliSense and F5 know about it.
- LNK1104 on Phazite.exe means the app or a debug session is still running: ask the user to close it.

## Submodules and third-party code

- After cloning, pulling or switching branches, run `git submodule update --init --recursive --depth 1` (`--depth 1` skips the dependencies' history, which for JUCE is large).
- Everything under `external/` is read-only: don't edit, reformat or "fix" it. Don't stage a changed `external/*` pointer unless the task is a deliberate dependency bump; before committing, check `git status` for "(new commits)".
- Never add a second copy of JUCE.
- The GitHub Actions in `.github/workflows/ci.yml` are pinned to full commit hashes; keep them pinned when updating.
- Never run `git submodule update --remote`: it would move every dependency off the commit Phazite pins. The submodules are shallow clones, so to bump one (JUCE, say) use the full 40-character commit hash: `git -C external/JUCE fetch --depth 1 origin <full-sha>`, `git -C external/JUCE checkout --detach FETCH_HEAD`, `git add external/JUCE`, `git submodule update --init --recursive --depth 1`. Review the changes on GitHub (compare old...new) and read JUCE's `BREAKING_CHANGES.md`, then reconfigure with `--fresh` and rebuild. For a JUCE bump, go through `docs/juce-workarounds.md` too: remove what the new JUCE fixed, and check what leans on JUCE's insides. The pre-commit hook refuses pin changes, so commit a bump with `git -c phazite.allowSubmoduleBump=true commit -F <file>`.
- Phazite is AGPL-3.0-or-later. Only add code under compatible licences (GPL-3.0, AGPL-3.0, LGPL-2.1-or-later, LGPL-3.0, MIT, BSD-2-Clause, BSD-3-Clause, Apache-2.0, ISC, Zlib, BSL-1.0 (the Boost Software License); not the 4-clause BSD licence). Fonts may also use the SIL Open Font License 1.1 (the UI font is Inter). Ship them as separate files next to the app, not compiled into it, together with their OFL text and copyright notice. An example song that someone else made ships as its notes alone (`resources/songs/*.mid`), under CC0 or CC BY only (people save what they make from it as their own, and those ask only for credit), credited in its description, its project's notes and `notices.json` with its license's text. Never compile in code that is under a proprietary licence alone, nor turn on a dependency's proprietary options. ## Real-time rules (audio thread)

The audio thread is the audio callback and everything it calls: Phazite's engine playing a block (`engine::Engine::process()`, with its worker threads, and every device's and plug-in's `process`), a helper's thread that plays a plug-in's blocks (`src/host/core/Instance.h`), and any helper reached from them. On the audio thread:
- No memory allocation or release: no `new`/`delete`/`malloc`, no growing `std::vector`/`juce::Array`, no creating `std::string`/`juce::String`, no allocating `std::function` captures. Allocate up front when preparing.
- No locks or waiting: no `std::mutex`, `juce::CriticalSection`/`ScopedLock`, condition variables, `WaitableEvent`, `MessageManagerLock`, or blocking calls into other threads.
- No posting to the message thread: no `triggerAsyncUpdate`, `sendChangeMessage` or `juce::MessageManager::callAsync` (they lock or allocate). Set an atomic flag instead and poll it from a `juce::Timer`.
- No file or network I/O, no logging (`DBG`, `juce::Logger`, `std::cout`), no system calls that can block.
- No throwing exceptions, no unbounded loops.
- Threads communicate through lock-free queues (FIFOs such as `juce::AbstractFifo`, or the engine's `engine::EventQueue`, `src/engine/core/EventQueue.h`, for several threads into one) and lock-free `std::atomic` values (add `static_assert (std::atomic<T>::is_always_lock_free)` for anything wider than a pointer), not shared mutable state; what the audio thread plays is handed to it whole and freed on the message thread (`src/engine/core/Handover.h`).
- Read parameters on the audio thread from what the engine holds of them (a device's values set by hand in `engine::DeviceNode`, atomics the message thread sets, and the plan's automation curves), never through `juce::ValueTree`, `juce::CachedValue` or other message-thread objects.
- The device list (`phazite::getDeviceTypes()`) offers Phazite's own devices and the plug-ins found by scanning, which play in helper processes. Phazite's devices follow these rules, and each has a guarded scenario in the real-time audit.
- `docs/realtime-audit.md` lists what is known to break these rules (in JUCE's code, or a plug-in's in its helper) and what Phazite does about each. After changes that touch playback, run the audit (`phazite_tests.exe --test-suite=realtime-audit` from the `windows-debug` build): it counts allocations on the audio thread and shows where they come from. Its guarded scenarios fail if steady playback allocates.

## Architecture rules

The code is layered so that the UI can change without touching the rules of editing, every edit can be tested without a window, and parts of the engine could be replaced later (`docs/design.md`, section 24). The roadmap's architecture track (phases A0 to A6) moves the existing code there; new code follows these rules now. `docs/architecture.md` draws the layers and explains these rules for contributors.
- Dependencies point down: `src/app/` may include `ui/`, `services/` and `model/`; `src/ui/` may include `services/` and `model/`; `src/services/` may include `model/`; `src/model/` includes none of them, but `engine/`, Phazite's playback engine, which includes only `devices/`, and `sandbox/`, what Phazite shares with the helpers that host plug-ins, which includes only `devices/` too. `src/host/`, the helper program, includes `sandbox/` and `devices/`, and no layer includes it. Every layer may include `devices/`, which includes none of the others. Tests and tools may include anything.
- Inside `src/ui/`, each folder uses only the folders before it (and the model and services), in this order: `theme/`, `components/`, `input/`, `devices/`, `timeline/`, `playlist/`, `pianoroll/`, `audioclip/`, `mixer/`, `browser/`, `project/`, `versions/`, `shell/`.
- No window code below the UI: `src/model/`, `src/services/`, `src/engine/`, `src/sandbox/` and `src/devices/` include no JUCE window module (`juce_gui_basics`, `juce_gui_extra`) and name no window class (`juce::Component`, `juce::KeyPress`...); `juce_graphics`, for `juce::Colour` values, is allowed in the model and services for now. Key and mouse handling, pixel sizes and how values are shown belong in `src/ui/`.
- Devices, the engine and the sandbox are engine-neutral: `src/devices/`, `src/engine/`, `src/sandbox/` and the helper program, `src/host/`, know nothing of the song model or the layers above. Phazite's engine plays a device through `engine::DeviceRunner` and `DeviceNode` (`src/engine/nodes/`), which hand it the audio, the notes and its parameters' values; the model compiles the song into what the engine plays (`src/model/playback/internal/SongPlayer.h`).
- `src/devices/` uses JUCE's `juce_core`, `juce_audio_basics` and `juce_dsp` only, and Rubber Band, and nothing of the other layers, so that a device could run on another engine. `src/engine/` uses JUCE's `juce_core`, `juce_audio_basics` and `juce_dsp`, r8brain-free-src and `src/devices/`, and nothing of the layers above. `src/sandbox/` uses JUCE's `juce_core`, `juce_events` and `juce_audio_basics` and `src/devices/`, and nothing of the layers above.
- `phazite_core` (the model, the services, the engine, the sandbox and the devices) compiles JUCE, once, for the app, the helper program, the tools and the tests: only `phazite_core` links the JUCE module targets, and every other target uses `phazite_use_core()` in `CMakeLists.txt`. JUCE options (compile definitions) go on `phazite_core`, never on another target. The tests' real VST3s (`tests/vst3/`) are the one exception: each is a `juce_add_plugin` target that compiles its own JUCE with its plug-in definitions, built only for `phazite_tests`, never installed.
- The UI decides nothing about the project: UI code doesn't start undo steps or change the project; it runs a command or calls a model function, and a control changes a parameter through a `ParameterHandle`. Phase A2 moved the UI's undo steps and edits into the model.
- The model's insides stay in the model: `src/ui/` includes no model `internal/` header (those take the song, its elements or what plays it), and doesn't reach them through `auto` or aliases either. Call a model function that takes and returns Phazite's own types (IDs, plain values, handles), and add one, with a test, if there is none. A model header that takes the song or its elements goes in its area's `internal/` folder; the model's other headers stay what the UI may use.
- Every change to a project is one named undo step with one owner: a command (through `undoTarget`; the registry opens the step), or a model function that is a change of its own (its comment says so, as `addDeviceTo()`'s does), which begins with `phazite::UndoStep` (`src/model/commands/internal/Undo.h`). Other model functions make their changes through the song's undo history (`Song::getUndoManager()`, `src/model/base/Song.h`) and never begin a step, so their changes join the caller's step; an `UndoStep` begun inside another for the same song joins it. A change that spans several events, such as a drag, is a `phazite::Gesture` (`Undo.h`): one named step from its start to its commit, which `UndoStep`s begun meanwhile join, or rolled back (`rollBack()`, for Escape during a drag: `TimelineEditor::cancelDrag()` in the timeline editors, `ParameterHandle::cancelGesture()` for a control, which a `ValueSlider` asks for through `onDragCancelled`) leaving nothing to redo. A trial (`phazite::Trial`, Swap's and a burst of the wheel's) is a step kept open across events; a song's history has one open at a time. View state is written without an undo manager. A command that moves the selected time range to what it made moves it with `RangeSelection::setInUndoStep()`, so that Undo puts it back; a range selected by hand isn't an undo step. What a new project starts with is added through `Project::create()`'s content function, which goes into its first save, so it is neither an undo step nor an unsaved change. Changes that are deliberately not undo steps (mute and solo, freezing a track, the loop, view state) are model functions too.
- View state (track heights, collapsed and pinned tracks, drum mode and drum rows, both editors' grid settings, where a device's window was) is saved, but written without an undo step and doesn't count as an unsaved change (decision 4). Each name's description in `Schema.h` says what it is (its kind, and whether it counts as a change), and must stay exact: `schema::isTrackViewProperty()`, `isGridProperty()`, `isDeviceViewProperty()`, the PIANOROLL and LANES elements, and `schema::isUncountedProperty()` / `isUncountedElement()` read the descriptions, for the project's notifications and its comparison with the saved copy, and for the versions' differences, alike.
- What leaves the song takes what names it along, in the same undo step: a function that removes a device, a chain, a send, a fader or a track calls `forgetWhatNamesTheGone()` (`src/model/mixer/internal/Mixer.h`), which removes the modulations of what is gone, the sends to a return that is gone and a removed drum sampler's pad tracks; a merge and an applied song run it too. Audio and notes don't share a track, and only tracks hold clips (not folders or returns): a model function that puts a clip on a track asks `canTrackHold()` (`src/model/arrangement/internal/Clips.h`).
- Every name Phazite writes into a project file is defined once, in `src/model/base/internal/Schema.h`, by its description (`SchemaDescription.h`), so that no name exists without one: an `Element` with the elements it goes in, or a `Property<T>` with the elements it is on, the C++ type of its value and what its comment says of it as facts (its range or its words, its default, its kind, whether it counts as a change); read and write the song's data only through those names and the song (`Song::getState()`). A device's type and parameter IDs, in its description in `src/devices/`, are saved too (`Schema.h` says how; a choice's value is saved as its number). Save Phazite's own values (names or Phazite's enums), never a library's enum number.

## Code conventions

- Every C/C++ file starts with `// SPDX-License-Identifier: AGPL-3.0-or-later`.
- C++20. Include JUCE's module headers directly (`<juce_gui_basics/juce_gui_basics.h>`), not `JuceHeader.h`. Qualify `juce::`.
- Use JUCE as it is documented to be used. Code that works around JUCE (a bug of its, something it lacks or keeps to itself, or a behaviour it doesn't promise) gets an entry in `docs/juce-workarounds.md` and ends its comment with `JUCE workaround <number> (docs/juce-workarounds.md)`, in the same change; code that stops working around it loses both. Code shaped by JUCE's documented behaviour is a correct pattern: it needs no marker.
- Never end a thread by force: on Windows, `TerminateThread` (which `juce::Thread::stopThread` with a time limit, and JUCE's `ThreadPool` after half a second, use) can leave a lock the thread held held for ever, and a loader lock left so hung every thread started after it (2026-11-10). Wake or cancel what a thread waits on, then `stopThread (-1)`; run jobs with `phazite::BackgroundJobs` (`src/model/base/BackgroundJobs.h`); and stop the thread of a JUCE class that stops its own with a time limit as it goes (`juce::AudioThumbnailCache`'s `getTimeSliceThread()`) with `stopThread (-1)` first. `tools/check-architecture.sh` counts the rest (`thread-kills`).
- Create and destroy songs, projects, project contexts and the engine context on the message thread, and destroy every project context before the engine context it plays on.
- Every user action is a command in `phazite::CommandRegistry` (`src/model/commands/CommandRegistry.h`, which has no UI code; menus, keys and the shortcuts editor reach it through `ui::CommandBridge` and `ui::KeyDispatcher` in `src/ui/input/`). Give it a stable id (`category.action`, e.g. `edit.undo`), a name, a one-sentence description and search synonyms. Set `undoTarget` to the song's undo history if it changes a project (`undoTargetOf()` in `src/model/commands/internal/Undo.h`, or the context's `getUndoManager()`), so it becomes one named undo step. Menus, shortcuts and the command palette use the registry; default shortcuts belong in the keymaps in `resources/keymaps/` (JUCE key descriptions, "command" for Ctrl/Cmd), not in code. While the computer keyboard plays notes, Shift and a letter run that letter's single-key shortcut (the owner's decision, as in Ableton Live), so a keymap must not give Shift and a letter a different command than the letter alone. When commands share a key, the enabled one with the highest `keyPriority` runs: note commands use `Command::notePriority`, so the arrow keys move selected notes and otherwise select tracks. A held key runs its command once; set `repeatsWhileHeld` on commands that take a step (nudging, zooming, transposing, moving through tracks, undo) so that they repeat while it is held. Set `overPlugins` on a command whose key should work while a plug-in window has the keyboard focus (play and stop do). While a mouse button is down, a key runs only the commands on the list in `src/ui/input/KeyDispatcher.cpp` (play and stop, the tools, the editors' zoom), none of which can change the song, its undo history or its files; every other command waits for the mouse to go up, so a new command is added to that list only if it changes nothing (`tests/EditorDragTests.cpp` presses every command in the middle of a drag). The time line's commands (zoom, grid, tools, nudge, quantize) act on the editor used last (`addTimelineCommands()` in `src/ui/timeline/TimelineEditor.h`).
- Keep registrations declarative: a command's perform, isEnabled, isTicked and currentName each call one named function from the area's header, which a test calls directly; with the song, through `withSong()`/`ifSong()` (`src/model/commands/internal/Undo.h`). Don't hide logic in registration lambdas or in anonymous-namespace helpers behind them. A switch for several things uses `toggleAll()`/`areAllOn()` (`src/model/base/Toggles.h`). The command goldens (`tests/golden/commands/`) record the catalogue and each command's states: change them on purpose, together with the command.
- Undo and redo with `phazite::undo()` and `redo()` (`src/model/commands/internal/Undo.h`): a step in the song's history, which what plays follows (the song's playback session hears the song change), the values set by hand included. Only they and the undo code (`Undo.h`: a gesture's roll-back, a trial, the held steps) move a song's history, never `juce::UndoManager::undo()` or `redo()` on it directly: what follows a move (the history's listeners, `Song::HistoryListener` in `src/model/base/Song.h`: the automation writer, through the playback session) is told from there, once the move is whole. A history listener begins no undo step and changes nothing of the song while it is told (`Song::History::tellMoved()` asserts it): what it would write it writes later, as the automation writer does at the next turn of the message loop, in a step of its own.
- The open project is the `ProjectContext` (`src/model/project/ProjectContext.h`) that `ProjectSession` owns: its song (which its `Project` owns), what is selected in it (one `phazite::Selection`, `src/model/base/internal/Selection.h`: tracks, clips, sections and devices held by IDs, which views reach by IDs: `getSongSelection()`; notes by their references among the clips the piano roll shows; automation points by their keys in the song's curves, which no file holds), the time range selected across tracks (by beats and IDs: `getSongRange()`), and the song's playback session, its clip renders, its clipboard and what remembers the parameter touched last. Only `ProjectSession` (and tests) changes which song it holds. Views listen to it (`ProjectContext::Listener`): for another project, and for what changed in the song, in groups (`SongChanges`), once a turn of the message loop. They name what they show by ID and forget it when another project opens, whose items can have the same IDs (the app closes menus then, as theirs capture IDs); `getProjectNumber()` tells them another project from the same one again. Its header has none of the model's insides: model and app code that holds the context finds the open song with `findSong (context)`, the selection with `getSelection (context)`, the range with `getRangeSelection (context)` and the playback session with `getSession (context)` (`src/model/project/internal/ProjectContext.h`, which also has the session's `setSong()`); model commands that act on the selection take the `Selection` (as `addTrackCommands()` in `src/model/arrangement/internal/Tracks.h` does) and use `selection.getSong()`, the same song. Model functions that make something select it in the `Selection` themselves; don't pass song getters around.
- Make the engine context once, with `phazite::createEngineContext()` (`src/model/engine/internal/EngineContext.h`): the app's as it starts, which outlives every project context, and the tests' one for all of them. Open saved projects with `Project::open()`: a project file is the song alone, which `makeSong()` (`src/model/project/internal/Project.h`) makes a `Song` of, with what every song has added, on the message thread.
- What devices hold of their state outside the song's undo history (a plug-in's own settings, program and channel layout) is stored into the song with `Song::storeDeviceStates()` (`src/model/base/Song.h`), before the song is saved and before it copies a track or a device; the song's plug-ins' instances set the store (`src/model/plugins/internal/PluginInstances.h`), and a change a plug-in makes in its own window counts as an unsaved change (`Song::markChangedOutsideHistory()`). `Project` writes the song alone into its files. The message thread waits for no plug-in as a project opens, saves, auto-saves or closes: a project's plug-ins load in the background and join the song as each is ready (`getPluginsLoading()` names those still loading, and a render started meanwhile says so and doesn't start), a save asks them for their states without waiting and writes when the answers are in (`PluginInstances::whenStatesIn()`), keeping the state a plug-in gave last if it doesn't answer, and helpers end on threads of their own. New code that needs a plug-in's answer asks the same way, never with a wait on the message thread.
- The song's end is `phazite::getSongEnd()` (`src/model/transport/internal/Playback.h`): the end of the bar its last clip ends in. The playlist's scrolling and Zoom to Fit use `getTimelineEnd()` (`src/model/arrangement/PlaylistModel.h`), which counts the sections and the chord lane too, on purpose.
- Keep the build warning-free under JUCE's recommended warning flags (/W4 on MSVC). Don't silence a warning without saying why.
- Formatting comes from `.clang-format` (JUCE style). After editing C/C++ files, run `sh tools/format.sh` with the Bash tool (on Windows it uses the clang-format 23 bundled with VS Code's C/C++ extension), and check with `sh tools/format.sh --check`. Don't hand-align code or trailing comments that the formatter will undo; use `// clang-format off` / `// clang-format on` only where a hand layout carries meaning (such as a table).
- Build controls from the base controls (`src/ui/components/Controls.h`): they give keyboard use and screen-reader names and values. Link a control to a parameter with `ui::ParameterAttachment`, giving it a `phazite::ParameterHandle` (`src/model/devices/ParameterHandle.h`) that the model hands out (`src/model/mixer/MixerModel.h`, `DeviceHandle.h`), which owns each change's named undo step; a meter shows a `phazite::LevelSource` (`src/model/mixer/LevelSource.h`). Give every control a title.
- Take colours and sizes from the tokens (`ui::getPalette (component)`), not literals. Icons are Lucide's (ISC; see `resources/icons/lucide/LICENSE`): to add one, copy its SVG from the same Lucide release into `resources/icons/lucide/`, list it in `juce_add_binary_data` in `CMakeLists.txt` and in `ui::Icon` (`src/ui/theme/Icons.h`), and show it with `ui::IconButton`. VS Code's name and icons stay out of the app.
- Every editor of Phazite's own devices fits the default dock without scrolling: build it on the shared frame (`src/ui/devices/DeviceEditorBase.h`, `DeviceLayout.h`), whose parts stack, show under tabs or narrow, with pages of them where the dock is narrower.
- On the time line (`src/ui/timeline/`), each part that draws the time line is added with `addTimelinePart()` and placed with `placeTimelinePart()`, never as a plain child, and what stays in view as the song scrolls, a clip's tag, is placed in `getShownTimeline()`, never in a part's own bounds; the view always starts on a whole pixel. Draw lines and edges with `beatToColumn()`, never by rounding `beatToX()`, and a line that changes along the song, a lane's, through `getLineSamples()`.

## Tests

`tests/README.md` lists the helpers and the suites.
- Tests are written with doctest; every test file includes `TestHelpers.h`. Add every new test file to `target_sources(phazite_tests ...)` in `CMakeLists.txt`.
- Tests of components include `UiTestHelpers.h`, whose `TestWindow` isn't on any screen; for a message another thread posts, wait for its effect with `dispatchMessagesUntil()`. A wait in a test waits for a condition, never for a time, and its limit is `hangTimeout` (two minutes, the default of `runTimersUntil()` and `dispatchMessagesUntil()`), which only a hang reaches: a shorter limit fails on a loaded machine. Reproduce a reported UI bug with such a test before fixing it.
- A test that builds a song does it through the model, as the UI does, with `TestSong.h`: what it builds then keeps working as the model's insides change. A test that needs a song without a project makes it with `phazite::createSong()` (`src/model/project/internal/Project.h`) and builds it through the model too, by the song and IDs: its tracks through `src/model/arrangement/internal/Tracks.h`, its clips and notes with `TestClips.h`, its devices with `TestDeviceValues.h` (by IDs: a test reads what the song holds of a device through `copyDevice()` and never builds, reads or writes a live song's device elements).
- A test that needs a real VST3 uses those of `tests/vst3/TestVst3s.h`, scanned and loaded as a user's plug-in is (`tests/Vst3PluginTests.cpp`). A test that needs a plug-in (a VST3) uses the stand-in in `TestPlugin.h`, which loads in the tests' helper as every plug-in does, or the stand-ins with `SandboxedPlugins.h`; a test that needs a device of its own uses `TestDevices.h`, which Phazite's engine plays as its own; a test that needs the whole window uses `AppScreen.h`; a test that plays the song through Phazite's engine drives it a block at a time with `EnginePlayback.h`, the same every time (with `Timing::asRender` where it compares what plug-ins in helpers play, whose blocks otherwise keep a deadline in real time, which a busy machine can miss).
- `tests/ScrollingFrameTests.cpp` checks what the playlist and the piano roll show from frame to frame while they follow the playhead: add what a change draws on the time line to its song.
- What threads share without a lock is raced on real threads for a fixed count of operations in `tests/LockFreeTests.cpp` (the event queue, the handover, the playhead's stamps, the transport): add a case for a new one. They show a torn value on any machine; a wrong memory order only under CI's `linux-tsan`.
- A new reader of what comes from outside (a file, a helper's message) gets a case in `tests/FuzzTests.cpp`, seeded with real inputs; a test that loads a song checks it with `checkSong()` (`tests/SongCheck.h`).
- `tests/PerformanceGateTests.cpp` counts the work an edit makes (plans compiled, components, repaints, allocations) in every ctest run, so a change that makes Phazite do more per edit fails it on any machine; lower its counts with a change that does less. The benchmark gates (`--test-suite=benchmark-gate`) and the long run (`--test-suite=long-run`) run nightly (`.github/workflows/nightly.yml`), not in ctest.
- The golden tests (`--test-suite=golden`) compare what Phazite saves, plays, ships as presets and registers as commands, and the formats' test vectors, with committed files (`tests/golden/`, `resources/presets/`). A refactoring must leave them as they are: if one fails, the behaviour changed, so fix the code. When a change is meant to alter them (a new or renamed project property, a new sound), run that suite with the environment variable PHAZITE_UPDATE_GOLDEN=1 (never in CI), read `git diff tests/golden` (and `resources/presets`) in full, and say in the commit message why they changed. Golden renders never use anything random.

## Checks by stage

Every check runs before a change reaches `main`, each once, at the stage that needs it (the owner's decision, 2026-11-17: a round that ran the whole ctest for every agent and every commit, six agents building at once, and pushed nothing for 36 commits spent a third of its time waiting on builds and tests, and CI then found what none of them could: GCC's own warnings and tests that fail only in the release build).
- While changing code: build `phazite_tests` and run the test files of what changed (`ctest --preset windows-debug -R "<Name>Tests"`, or the test program with `--source-file=*<Name>*`), not the whole ctest.
- Before handing a change over: those files, the nets its kind needs ("Before reporting work as done"), `sh tools/check-architecture.sh` and `sh tools/format.sh --check`.
- Before a batch of changes is committed to the work branch: one whole build and `ctest --preset windows-debug`, with no other build or test running on the PC. A change of docs alone needs neither.
- Work goes on a branch, pushed every few commits so that CI builds it on the presets the local build doesn't check (`windows-release`, `linux-release`, `linux-asan`, `linux-tsan`, `linux-clang`; a compile error shows there in 10 to 15 minutes, the whole run in about half an hour); don't wait for it, read it when the next batch is ready. `main` moves only by fast-forward to a commit whose CI run passed on every preset, and when the owner asks for it: before that, start the full run on the branch's head (`gh workflow run ci.yml --ref <branch> -f full=true`) and wait for it to pass. A work branch saves its own presets' compiler caches only, and a deleted branch's caches are deleted (`.github/workflows/caches.yml`), so that `main`'s stay within GitHub's 10 GB: delete a branch once it is merged.
- A test that fails in some runs is fixed before other work, or entered in `docs/known-bugs.md` the same day: every later run pays for it.
- Benchmarks run only for performance work, before and after, on a quiet machine, with `main` built beside the branch: the numbers on `docs/performance.md` are a record, not a baseline.

## Agents

- An orchestrator runs at most three agents that build at once on this PC (8 cores): more make every build slower and the timing tests fail.
- A fix agent builds `--target phazite_tests` and runs its area's test files and nets, never the whole ctest; the orchestrator runs that once for the batch.
- A brief names the files and the bugs in scope. An agent reports what else it finds instead of fixing it, unless it is small and in its own files.
- A fix that still fails after three attempts, or a review that still blocks after three rounds, is reported with what is known: the sound part is committed and the rest entered as a known bug.
- Every change is read by one reviewer agent before it merges; a second read covers only what a blocking finding changed.
- A test that fails beside other builds and passes alone is reported as that, not investigated by the agent.
- Agents commit and push nothing; the orchestrator commits, and pushes work branches.

## Committing

The repository will be public on GitHub, and a commit stays in its history even after a later commit deletes the file. The user's rule: nothing confidential may ever reach the remote. Before every commit:
- Read `git diff --cached` in full and check that nothing confidential is staged: API keys and tokens (including AI providers'), passwords, private keys, signing certificates, `.env` files, crash dumps, and personal data such as email addresses or local paths containing user names. If anything looks sensitive, stop and ask the user.
- Secrets never go in tracked files, including `.vscode/launch.json`, `CMakePresets.json` and `.claude/settings.json`. Keep them in environment variables or in files git ignores (`.env`, `CMakeUserPresets.json`, `.claude/settings.local.json`).
- The git hooks (`.githooks/`) also stop a commit, merge or push whose email isn't a GitHub noreply address, or whose changes or messages gitleaks flags. They don't replace reading the diff. Never skip them with `--no-verify` (commit or push), never change `core.hooksPath`, and never use `-c phazite.allowPublicEmail=true` unless the user asks; if a hook stops something, show the user its message and ask how to proceed. For a false positive the user has checked, add `gitleaks:allow` to that line, or add the printed `Fingerprint` line to `.gitleaksignore` where comments aren't possible.
- The pre-commit hook also refuses changed dependency pins (`external/`, `.gitmodules`), staged files over 5 MiB, new audio, video and picture files, trailing whitespace, leftover conflict markers, unformatted C/C++ and code that doesn't match the architecture budgets. Fix the cause; use `-c phazite.allowSubmoduleBump=true` only for a deliberate bump, `-c phazite.allowLargeFiles=true` or `-c phazite.allowMedia=true` only when the user asks, and `-c phazite.allowBudgetIncrease=true` only as "Architecture rules" says.
- Stage a new or changed hook with `git add --chmod=+x .githooks/<name>`: Windows records no executable bit, and git on Linux and macOS silently skips a hook without it. `git ls-files -s .githooks` must show mode 100755.
- In WSL/Linux the hooks need gitleaks 8.19 or newer from its GitHub releases (Ubuntu's own package is 8.16) and `git config core.hooksPath .githooks` once per clone.
- Commit messages: write them to a file and use `git commit -F <file>`. Windows PowerShell 5.1 splits a `-m` argument at embedded double quotes.
- Work branches may be pushed without asking (the owner, 2026-11-17), after the diff of every commit on them was read as above. Never push `main`, push a tag, force a push or add a remote unless the user asks.

## Before reporting work as done

- Build `windows-debug` (and `windows-profile` or `windows-release` for performance-related work), run `ctest --preset windows-debug` and `sh tools/check-architecture.sh`, once for the batch ("Checks by stage"), and report the commands, their exit codes and any warnings or failing tests, and the state of CI's run on the branch's head.
- The nets a change must keep whole (`tests/README.md`, "The nets"): a new model command is run in the command script (`tests/CommandGoldenTests.cpp`), or listed in `getCommandsNotRun()` with why; a new saved name is added to the representative golden project (`tests/GoldenProjectTests.cpp`), or to `getNamesNotInTheProject()` with why; a test of what playback promises everywhere runs at every condition (`atEveryCondition()`, `tests/PlaybackConditions.h`); a golden song that can't play live as it renders says why (`liveDiffers`); a JUCE assertion fails the test it fires in (`tests/TestMain.cpp`): fix what raises it, or list it in `allowedAssertions` with why and in `docs/juce-workarounds.md`; an edit that could make the audio thread allocate gets a scenario in the real-time audit that makes it while the song plays (`Edit` in `tests/RealtimeAuditTests.cpp`), and a real-time test waits for blocks played, never for time (`waitForBlocks()`, `tests/RealTimePlayback.h`); a tool or a gesture of an editor is tested with the mouse on an `EditorScreens.h` screen, with what happens when the song changes under it; a device that can't keep a rule of the conformance suite (`tests/DeviceConformanceTests.cpp`) gets a line in its `exceptions` table with its reason and a known bug, never a looser rule; and a change to a project is checked with `UndoCheck` (`tests/UndoCheck.h`) where its Undo could go wrong.
- For performance-related work, run the benchmarks from `windows-profile` (`phazite_tests.exe --test-suite=benchmark --no-skip`, in `tests/Benchmarks.cpp`; ctest skips them) before and after, and update the numbers in `docs/performance.md`.
- Commit lowered architecture budgets with the change that lowered them.
- After a push, check the CI run for that commit (https://github.com/august-byrne/Phazite/actions). The repository is public, so the GitHub REST API (`/repos/august-byrne/Phazite/actions/runs`) answers without signing in.
- For audio or UI changes, tell the user what to click and listen for, because the GUI can't be checked from the shell.
