# Phazite

Open-source DAW (AGPL-3.0-or-later) in C++20 on Tracktion Engine + JUCE. It hosts VST3 plug-ins (AU on macOS later). Performance and low resource use matter in both the audio engine and the UI.

## Build

Run every command from the repository root. The presets are the only entry point, and the same two commands work on every OS.

- `cmake --list-presets` shows the presets for this machine: `windows-debug`, `windows-release` on Windows; `linux-debug`, `linux-release`, `linux-asan`, `linux-tsan` on Linux/WSL.
- Configure: `cmake --preset <preset>`. Build: `cmake --build --preset <preset>`. Test: `ctest --preset <preset>`, after a build of the same preset (it runs `phazite_tests`; all passed when it prints `100% tests passed` and exits 0). To run some tests only, call the test executable directly, for example `build\windows-debug\phazite_tests_artefacts\Debug\phazite_tests.exe --test-case="*save*"`.
- Run configure and build as separate commands, each with run_in_background and without redirections or pipes (no `>`, `*>`, `2>&1`, `Tee-Object`): the complete output lands in the task's output file. When a command finishes, check its exit code and search that file case-insensitively for `error` and `warning` (this also catches "CMake Warning"), plus `D9` and `LNK4`. The first configure of a build folder also builds JUCE's `juceaide` helper (1-2 minutes); a full build takes several minutes.
- On Windows the shell is Windows PowerShell 5.1: there is no `&&`/`||`, and `;` does not stop after a failure. Use separate commands, or `A; if ($LASTEXITCODE -eq 0) { B }`. In WSL/Linux the shell is Bash.
- Never run vcvars/VsDevCmd, open a Developer PowerShell, or call `cl`, `link`, `msbuild` or `ninja` directly. MSVC is found by `cmake/toolchains/windows-msvc.cmake`, which wraps `external/WindowsToolchain`.
- After a Visual Studio Build Tools update (new MSVC version) or a toolchain change, reconfigure with `cmake --preset <preset> --fresh`. If that folder still fails, delete `build\<preset>` and configure again.
- Before configuring or building, run `@(Get-Process -Name cmake, ninja -ErrorAction Ignore).Count`. If it prints anything other than 0 and you didn't start those processes (VS Code may be building), ask the user before continuing: two builds in one folder break each other.

## Tools (Windows)

- `tools\setup-windows.cmd` installs or updates every tool (including gitleaks) and turns on this clone's git hooks (`core.hooksPath = .githooks`). A full run needs the user at a UAC prompt and can take up to an hour (a few minutes when everything is current), so start it only when the user asks (as a background command) or ask them to run it. `tools\setup-windows.cmd -CheckOnly` is safe at any time: no admin rights, changes nothing.
- Exit codes (your shell tool shows 3010 as 194; the script's last line, "Result: ...", always states it): 0 = done; 3010 = done, but Windows must restart (ask the user to reboot, then run it again); 1 = a step failed (read the FAILED lines and the log path it prints); 2 = it could not start. With `-CheckOnly`: 0 = all present, 1 = something missing (including this clone's git hooks) or not on this shell's PATH, 3010 = Visual Studio is waiting for a reboot. Switches: `-CheckOnly`, `-SkipUpdates`, `-WithTestPlugin` (Surge XT), `-WithLlvm`, `-SkipVSCodeExtensions`.
- If `cmake` or `git` is "not recognized", run `tools\setup-windows.cmd -CheckOnly`. If it finds the tools, the program that started Claude Code has an old PATH: ask the user to quit every VS Code window, start VS Code from the Start menu and close any terminals it restores (or to open a new terminal and start Claude there). If it reports MISSING, ask the user to run the setup. Don't edit PATH or search the disk for tools. If it prints `hooks ... OFF`, the git hooks are off in this clone: tell the user, then run `git config core.hooksPath .githooks` (no admin rights or full setup needed).

## Running and debugging

- The app is `build/<preset>/Phazite_artefacts/<build type>/Phazite` (`.exe` on Windows), where the build type is `Debug` for `*-debug` and `linux-asan`, `Release` for `*-release`, and `RelWithDebInfo` for `linux-tsan`. Run the TSan build as `TSAN_OPTIONS=suppressions=tools/tsan-suppressions.txt setarch $(uname -m) -R build/linux-tsan/Phazite_artefacts/RelWithDebInfo/Phazite`. That file lists known races in Tracktion, each explained in `docs/realtime-audit.md`; a race in Phazite's own code is fixed, never suppressed.
- The app is for the user to run, or to start with F5 in VS Code. Don't start it from the shell unless asked; then use `Start-Process <path>` (a bare call blocks the tool until the window closes). Tell the user what to click and listen for.
- Debugging: VS Code's "Phazite (Windows)" launch configuration (F5) builds the active preset and starts the app under the debugger. A crash outside a debugger leaves a dump in `%LOCALAPPDATA%\CrashDumps\Phazite.exe.*.dmp`; open it with the "Open crash dump (Windows, Debug build)" configuration. Only `windows-debug` builds have symbols, so reproduce Release crashes there.
- VS Code configures only on request. After a build folder was created from the shell (first configure, or after deleting `build\<preset>`), ask the user to run "CMake: Configure" once in VS Code so IntelliSense and F5 know about it.
- LNK1104 on Phazite.exe means the app, its `--PluginScan` child or a debug session is still running: ask the user to close it.

## Repository layout

- `src/app/` - the app: startup (`Main.cpp`), the main window with its menus and dialogs (`MainWindow.*`), the open project (`ProjectSession.*`), the services it owns (`AppServices.*`: the settings, recent projects, the Phazite Sounds download, the library and the previewer, which it hands to what needs them), and the registration of the commands that work on the open song (`AppCommands.*`, in the order the app uses). Everything but `Main.cpp` is in the `phazite_app` static library, which the tests link too; the `Phazite` target is `Main.cpp`.
- `src/ui/` - the window's components, in the `phazite_ui` static library, which the app and the tests link; one folder per area, each using only the folders before it (and the model and services):
  - `theme/`: `ui::LookAndFeel`, the design tokens (`DesignTokens.h`: colours, text sizes, spacing) and the icons. Take colours and sizes from the tokens (`ui::getPalette (component)`), not literals. Icons are Lucide's (ISC; see `resources/icons/lucide/LICENSE`): to add one, copy its SVG from the same Lucide release into `resources/icons/lucide/`, list it in `juce_add_binary_data` in `CMakeLists.txt` and in `ui::Icon` (`Icons.h`), and show it with `ui::IconButton`.
  - `components/`: the base controls (`Controls.h`: `ui::Knob`, `ui::Fader`, `ui::LevelMeter`) and how values read as text (`ValueText.h`: decibels, pan). Build controls from the base controls: they give keyboard use and screen-reader names and values. Until architecture phase A3 brings Phazite's own parameter handles, link a control to a device parameter with `ui::ParameterAttachment`, which also names the undo step; it still takes Tracktion's plug-in and parameter ID, so get those from a model function and keep other Tracktion types out of new UI code. Give every control a title.
  - `input/`: the commands as JUCE's menus, key mappings and shortcuts editor see them (`CommandBridge.*`), the keys that run them (`KeyDispatcher.*`: priorities, held keys, the Shift rule, keys over plug-in windows), the keymaps (`Keymap.*`) and the user's changes to them, kept in the settings (`KeymapStore.*`), menus and tooltips that show commands with their shortcuts (`CommandUI.*`), the computer keyboard (`ComputerKeyboard.*`), the main window's keys (`WindowKeys.*`: the computer keyboard is asked before the shortcuts), and `PluginKeys.*`, which lets play, stop and the computer keyboard work over plug-in windows.
  - `devices/`: the menus that add instruments and effects (`DeviceMenus.*`) and devices' windows (`PluginWindow.*`).
  - `timeline/`: what the playlist shares with the piano roll: the time line, grid and tools (`TimelineEditor.*`, `SmartTool.*`).
  - `playlist/` (`Playlist.*`, `TrackHeader.*`, `ClipComponent.*`, `SectionsStrip.*`), `pianoroll/` (`PianoRoll.*`, with its parts declared in `PianoRollParts.h`), `mixer/` (`MixerView.*`, `ChannelStrip.*`), `browser/` (`Browser.*` and the F8 plug-in picker `PluginPicker.*`), and `shell/`: the window's content (`AppShell.*`) with the top bar, hint bar, command palette, panels, settings and the welcome window (`Welcome.*`).
- `resources/` - keymaps, song outlines (`outlines/*.outline.json`) and icons (compiled in as `PhaziteData`), and fonts (Inter, copied next to the app into `fonts/` after each build).
- `src/model/` - Phazite's project model on top of Tracktion, without window code, in the `phazite_core` static library, one folder per area: `commands/` (the command registry, and undo and redo with the undo convention, `Undo.h`), `engine/` (`createEngine()`, `loadEdit()`, live MIDI, previews, the loudness meter plug-in), `project/` (the project folder, saving and autosave, the starter project), `transport/` (playback and the loop), `arrangement/` (tracks, clips, sections and song outlines, the grid, the selection, time edits, importing files), `notes/` and `mixer/`; below them all, `base/` (`Tracktion.h`, the one header that includes Tracktion Engine, and `Schema.h`, the names of everything Phazite writes into a project file). That library also compiles Tracktion Engine and JUCE, once, for the app and the tests: only `phazite_core` links the JUCE/Tracktion module targets, and every other target uses `phazite_use_core()` in `CMakeLists.txt`. JUCE and Tracktion options (compile definitions) go on `phazite_core`, never on another target.
- `src/services/` - what the app keeps outside any project, also compiled into `phazite_core`: settings (`Settings.*`: every key in one list), recent projects (`RecentProjects.*`), the browser's library (`Library.*`: sounds, search, favorites) and the Phazite Sounds download (`SoundPack.*`). Services may use the model; the model never uses them.
- `tests/` - unit tests in the `phazite_tests` target, which links `phazite_app` and `phazite_ui`, written with doctest (MIT, bundled with Tracktion; include `TestHelpers.h`). Add every new test file to `target_sources(phazite_tests ...)`. Tests of components include `UiTestHelpers.h`: a `TestWindow` that isn't on any screen (it works headless, as on Linux CI), through which a `Mouse` and `pressKey()` reach the components the way JUCE delivers real events, mouse and key listeners included; `dispatchPendingMessages()` delivers async updates: every message posted before the call, and what those post in turn; for a message another thread posts, wait for its effect with `dispatchMessagesUntil()`. Reproduce a reported UI bug with such a test before fixing it. The golden tests (`--test-suite=golden`: `tests/*Golden*.cpp`, `tests/MigrationTests.cpp` and the catalogue case in `tests/AppShellTests.cpp`) compare what Phazite saves (`tests/golden/projects/`), plays (`tests/golden/renders/`: level fingerprints of offline renders, never audio), the model's commands (`tests/golden/commands/`: ids, texts, switches and order; a script that runs each of them, with the saved result, the undo step each makes, and every command's enabled, ticked and name state along the way; and every command the app registers, in order, with its keys, `app-catalogue.txt`), and how projects saved by earlier versions open (`tests/golden/legacy/`, never rewritten) with committed files. A refactoring must leave them as they are: if one fails, the behaviour changed, so fix the code. When a change is meant to alter them (a format migration, a new project property), run that suite with the environment variable PHAZITE_UPDATE_GOLDEN=1 (never in CI), read `git diff tests/golden` in full, and say in the commit message why they changed. Golden renders never use 4OSC or anything else random.
- `docs/design.md` - the product design: what Phazite should be and why, with the owner's decisions and the open questions. `docs/roadmap.md` - the step-by-step build plan with "Done when" checks; update its status table after each step. Read both before starting feature work, and update `design.md` when a decision changes.
- `CMakeLists.txt`, `CMakePresets.json`, `cmake/` - build definition, presets, Windows toolchain wrapper and CMake helpers.
- `external/tracktion_engine` - git submodule: Tracktion Engine (`develop`, pinned commit), with JUCE as its own submodule at `modules/juce`. Never add JUCE separately.
- `external/WindowsToolchain` - git submodule (MIT), used on Windows at build time only.
- `tools/` - machine setup, `format.sh` (clang-format for the C/C++ files), `check-architecture.sh` (the architecture rules and their budgets in `architecture-budget.txt`; see "Architecture rules"), and `soundkit/`, the `phazite_soundkit` tool that renders and zips Phazite Sounds from the recipes in the phazite-sounds repository (run by hand; that repository's README). `build/<preset>/` - build output (ignored by git).
- `.clang-format` - C/C++ formatting rules: JUCE's coding standards, for clang-format 22 or newer (23 is used).
- `.github/workflows/ci.yml` - GitHub Actions: gitleaks over the whole history, clang-format 23.1.3, whitespace, the architecture budgets (`tools/check-architecture.sh --ci`); builds both Windows presets (VS 2026 on `windows-2025-vs2026`) and all four Linux presets (Ubuntu 24.04), all with warnings as errors. `.github/problem-matchers/` turns compiler messages into annotations, which the public API serves without signing in (`/repos/august-byrne/Phazite/check-runs/<job id>/annotations`); raw logs need a login. Actions are pinned to full commit hashes; keep them pinned when updating.
- `.githooks/` - git hooks, turned on per clone by `git config core.hooksPath .githooks` (the setup script does this). `pre-commit` checks the author and committer email (GitHub noreply only), dependency pins, files over 5 MiB, whitespace errors and conflict markers, secrets (gitleaks), formatting (`tools/format.sh --staged`) and the architecture budgets (`tools/check-architecture.sh --staged`); `pre-merge-commit` runs it for merges; `pre-push` checks every commit the remote doesn't have yet (emails, tags, gitleaks over changes and commit messages, and that every architecture budget raise says why in its message).

## Real-time rules (audio thread)

The audio thread is the audio callback and everything it calls: plug-in and graph processing (`applyToBuffer`, `process`, `processBlock`), Tracktion node processing, and any helper reached from them. On the audio thread:
- No memory allocation or release: no `new`/`delete`/`malloc`, no growing `std::vector`/`juce::Array`, no creating `std::string`/`juce::String`, no allocating `std::function` captures. Allocate up front when preparing.
- No locks or waiting: no `std::mutex`, `juce::CriticalSection`/`ScopedLock`, condition variables, `WaitableEvent`, `MessageManagerLock`, or blocking calls into other threads.
- No posting to the message thread: no `triggerAsyncUpdate`, `sendChangeMessage` or `juce::MessageManager::callAsync` (they lock or allocate). Set an atomic flag instead and poll it from a `juce::Timer`.
- No file or network I/O, no logging (`DBG`, `juce::Logger`, `std::cout`), no system calls that can block.
- No throwing exceptions, no unbounded loops.
- Threads communicate through lock-free queues (single-producer/single-consumer FIFOs such as `juce::AbstractFifo` or `choc::fifo::SingleReaderSingleWriterFIFO`) and lock-free `std::atomic` values (add `static_assert (std::atomic<T>::is_always_lock_free)` for anything wider than a pointer), not shared mutable state.
- Read parameters through their atomic value (`AutomatableParameter::getCurrentValue()`), never through `juce::ValueTree`, `juce::CachedValue` or other message-thread objects.
- Tracktion's built-in 4OSC synth locks and allocates on the audio thread. It is fine for the smoke test (and the device list offers it until step 1.6 brings Phazite's own synth), but not a pattern to copy or a basis for performance measurements. The device list (`phazite::getDeviceTypes()`) offers no other Tracktion device but the reverb: the others break these rules.
- Tracktion's own code breaks some of these rules; `docs/realtime-audit.md` lists what is known and what Phazite does about each. After changes that touch playback, run the audit (`phazite_tests.exe --test-suite=realtime-audit` from the `windows-debug` build): it counts allocations on the audio thread and shows where they come from. Its guarded scenarios fail if steady playback allocates.

## Architecture rules

The code is layered so that the UI can change without touching the rules of editing, every edit can be tested without a window, and parts of the engine could be replaced later (`docs/design.md`, section 24). The roadmap's architecture track (phases A0 to A5) moves the existing code there; new code follows these rules now.
- Dependencies point down: `src/app/` may include `ui/`, `services/` and `model/`; `src/ui/` may include `services/` and `model/`; `src/services/` may include `model/`; `src/model/` includes none of them. Tests and tools may include anything.
- No window code below the UI: `src/model/` and `src/services/` include no JUCE window module (`juce_gui_basics`, `juce_gui_extra`) and name no window class (`juce::Component`, `juce::KeyPress`...); `juce_graphics`, for `juce::Colour` values, is allowed for now. Key and mouse handling, pixel sizes and how values are shown belong in `src/ui/`.
- The UI decides nothing about the project: UI code doesn't start undo steps or change the project, except through `ui::ParameterAttachment` until phase A3; it runs a command or calls a model function. Phase A2 moves the UI's remaining undo steps and edits into the model.
- Tracktion stays in the model: don't add Tracktion includes or `te::` names to `src/ui/`, and don't hide them behind `auto` or aliases: the aim is a UI that doesn't depend on Tracktion, not a lower count. Call a model function that takes and returns Phazite's own types (IDs, plain values), and add one, with a test, if there is none. Phase A3 removes the Tracktion use left in the UI.
- Every change to a project is one named undo step with one owner: a command (through `undoTarget`; the registry opens the step), or a model function that is a change of its own (its comment says so, as `addDeviceTo()`'s does), which begins with `phazite::UndoStep` (`src/model/commands/Undo.h`). Other model functions pass the Edit's undo manager and never begin a step, so their changes join the caller's step; an `UndoStep` begun inside another for the same Edit joins it. View state is written without an undo manager. A command that moves the selected time range to what it made moves it with `RangeSelection::setInUndoStep()`, so that Undo puts it back; a range selected by hand isn't an undo step. What a new project starts with is added through `Project::create()`'s content function, which saves it and opens the project from that save, so it is neither an undo step nor an unsaved change. Changes that are deliberately not undo steps (mute and solo, the loop, view state) are model functions too.
- Every name Phazite writes into a project file is defined once, in `src/model/base/Schema.h`, with where it is stored and what it holds; read and write Phazite's data only through those names and `getPhaziteState()` / `findPhaziteState()`. Never rename one.
- Phazite's own settings (the `phazite*` keys) are read and written only through `phazite::Settings` (`src/services/Settings.h`), which lists every key once with its default and when it is saved; a new setting goes into that list. Never rename a key.
- Every colour, size, corner radius and font in the UI comes from the design tokens (`DesignTokens.h`, read with `ui::getPalette (component)`); if none fits, add a token rather than a literal. Phase A4 moves the tokens into a file a designer edits, with a gallery app, and the text the user reads into a strings table.
- Meters, the playhead and other values that change many times a second are read from small read-only sources polled by a `juce::Timer`, never stored in the project or sent as change messages.
- `tools/check-architecture.sh` counts what these rules forbid in `src/`, plus Tracktion includes in the model outside its prelude, undo steps begun in the model outside the undo code, model files on include loops, files directly in `src/model/` or `src/ui/`, `#include "..."` lines in `src/`, `tests/` and `tools/` that name no file exactly, and source paths in `CMakeLists.txt` that name no file exactly or C/C++ files it doesn't list (Windows forgives a wrong case or a header MSVC finds next to an includer; Linux doesn't), and compares each count with `tools/architecture-budget.txt`. CI's Checks job and pre-commit check 7 run it; pre-push checks raises. Run `sh tools/check-architecture.sh` (Bash tool) after changing `src/`, `tests/` or `CMakeLists.txt`. When a change removes matches, run `--update` and commit the lower budget with it; when it adds matches, change the code instead (`--list <rule>` shows each match). Raise a budget only when a plan step moves code between layers on purpose: put `Architecture-Budget-Raise: <rule> <old> -> <new>: <reason>` in the commit message (CI and pre-push check it; keep it when squashing) and commit with `git -c phazite.allowBudgetIncrease=true commit -F <file>`; otherwise ask the user.

## Code conventions

- Every C/C++ file starts with `// SPDX-License-Identifier: AGPL-3.0-or-later`.
- C++20. Include JUCE's module headers directly (`<juce_gui_basics/juce_gui_basics.h>`), not `JuceHeader.h`. Model and services code gets Tracktion from `src/model/base/Tracktion.h`, which includes `<tracktion_engine/tracktion_engine.h>` and declares `namespace te = tracktion;`. Qualify `juce::`.
- Create and destroy Tracktion objects (Engine, Edit) on the message thread, and destroy every `te::Edit` before the `te::Engine`.
- Every user action is a command in `phazite::CommandRegistry` (`src/model/commands/CommandRegistry.h`, which has no UI code; menus, keys and the shortcuts editor reach it through `ui::CommandBridge` and `ui::KeyDispatcher` in `src/ui/input/`). Give it a stable id (`category.action`, e.g. `edit.undo`), a name, a one-sentence description and search synonyms. Set `undoTarget` if it changes an Edit, so it becomes one named undo step. Menus, shortcuts and the command palette use the registry; default shortcuts belong in the keymaps in `resources/keymaps/` (JUCE key descriptions, "command" for Ctrl/Cmd), not in code. While the computer keyboard plays notes, Shift and a letter run that letter's single-key shortcut (the owner's decision, as in Ableton Live), so a keymap must not give Shift and a letter a different command than the letter alone. When commands share a key, the enabled one with the highest `keyPriority` runs: note commands use `Command::notePriority`, so the arrow keys move selected notes and otherwise select tracks. A held key runs its command once; set `repeatsWhileHeld` on commands that take a step (nudging, zooming, transposing, moving through tracks, undo) so that they repeat while it is held. Set `overPlugins` on a command whose key should work while a plug-in window has the keyboard focus (play and stop do). The time line's commands (zoom, grid, tools, nudge, quantize) act on the editor used last (`addTimelineCommands()` in `src/ui/timeline/TimelineEditor.h`).
- Undo and redo with `phazite::undo()` and `redo()` (`src/model/commands/Undo.h`), not `te::Edit::undo()`: Tracktion's undo puts back a parameter's stored value but not the value the engine plays with.
- What the user has selected lives in one `te::SelectionManager`, `ProjectSession::getSelection()`; commands that act on the selection or on the open project take it (as `addTrackCommands()` in `src/model/arrangement/Tracks.h` does) and find the project's Edit as `selection.getEdit()`. Put a track after another with `phazite::getInsertPointAfter()`, not `te::TrackInsertPoint (track, false)`, which means the start of the list for the first top-level track.
- Create the Engine only with `phazite::createEngine()` (`src/model/engine/EngineSetup.h`), never `te::Engine` directly: Tracktion's default settings storage writes the user's full name into every saved project. Load saved Edits with `phazite::loadEdit()` (on the message thread), not Tracktion's `EditLoader`.
- The song's end is `phazite::getSongEnd()` (`src/model/transport/Playback.h`): the end of the bar its last clip ends in. Not `te::Edit::getLength()`, which counts sections; only the playlist's scrolling and Zoom to Fit use that for the song, on purpose (the previewer uses it for the small Edit each sound plays in).
- Keep the build warning-free under JUCE's recommended warning flags (/W4 on MSVC). Don't silence a warning without saying why.
- Formatting comes from `.clang-format` (JUCE style). After editing C/C++ files, run `sh tools/format.sh` with the Bash tool (on Windows it uses the clang-format 23 bundled with VS Code's C/C++ extension), and check with `sh tools/format.sh --check`. Don't hand-align code or trailing comments that the formatter will undo; use `// clang-format off` / `// clang-format on` only where a hand layout carries meaning (such as a table).

## Committing

The repository will be public on GitHub, and a commit stays in its history even after a later commit deletes the file. The user's rule: nothing confidential may ever reach the remote. Before every commit:
- Read `git diff --cached` in full and check that nothing confidential is staged: API keys and tokens (including AI providers'), passwords, private keys, signing certificates, `.env` files, crash dumps, and personal data such as email addresses or local paths containing user names. If anything looks sensitive, stop and ask the user.
- Secrets never go in tracked files, including `.vscode/launch.json`, `CMakePresets.json` and `.claude/settings.json`. Keep them in environment variables or in files git ignores (`.env`, `CMakeUserPresets.json`, `.claude/settings.local.json`).
- The git hooks (`.githooks/`) also stop a commit, merge or push whose email isn't a GitHub noreply address, or whose changes or messages gitleaks flags. They don't replace reading the diff. Never skip them with `--no-verify` (commit or push), never change `core.hooksPath`, and never use `-c phazite.allowPublicEmail=true` unless the user asks; if a hook stops something, show the user its message and ask how to proceed. For a false positive the user has checked, add `gitleaks:allow` to that line, or add the printed `Fingerprint` line to `.gitleaksignore` where comments aren't possible.
- The pre-commit hook also refuses changed dependency pins (`external/`, `.gitmodules`), staged files over 5 MiB, trailing whitespace, leftover conflict markers, unformatted C/C++ and code that doesn't match the architecture budgets. Fix the cause; use `-c phazite.allowSubmoduleBump=true` only for a deliberate bump, `-c phazite.allowLargeFiles=true` only when the user asks, and `-c phazite.allowBudgetIncrease=true` only as "Architecture rules" says.
- Stage a new or changed hook with `git add --chmod=+x .githooks/<name>`: Windows records no executable bit, and git on Linux and macOS silently skips a hook without it. `git ls-files -s .githooks` must show mode 100755.
- In WSL/Linux the hooks need gitleaks 8.19 or newer from its GitHub releases (Ubuntu's own package is 8.16) and `git config core.hooksPath .githooks` once per clone.
- Commit messages: write them to a file and use `git commit -F <file>`. Windows PowerShell 5.1 splits a `-m` argument at embedded double quotes.
- Never add a remote or push unless the user asks.

## Before reporting work as done

- Build `windows-debug` (and `windows-release` for performance-related work), run `ctest --preset windows-debug` and `sh tools/check-architecture.sh`, and report the commands, their exit codes and any warnings or failing tests.
- Commit lowered architecture budgets with the change that lowered them.
- After a push, check the CI run for that commit (https://github.com/august-byrne/Phazite/actions). The repository is public, so the GitHub REST API (`/repos/august-byrne/Phazite/actions/runs`) answers without signing in.
- For audio or UI changes, tell the user what to click and listen for, because the GUI can't be checked from the shell.
