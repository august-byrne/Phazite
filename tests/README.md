# tests

Phazite's tests, in the `phazite_tests` target, which links `phazite_app` and `phazite_ui` and is written with doctest
(MIT, `external/doctest`, compiled into the tests only, as a system include with its warnings off). Each `*Tests.cpp` file holds the tests of one area; `ctest --preset <preset>` runs the
executable once for each test file. The rules for writing tests are in `CLAUDE.md`, "Tests".

## Helpers

| File | What it gives a test |
|---|---|
| `TestMain.cpp` | The test runner: doctest inside a JUCE environment. Before it ends it waits for the threads nothing else waits for (the library's walks, the missing files' checks) to end, so that none trips JUCE's leak detector as static objects go; one still under way at the tests' hang limit fails the run. On Windows it ends the program once every static object has gone (JUCE's leak detector has checked each class), with main()'s result, without the C runtime's teardown, during which a thread the graphics driver started once crashed it (known bug 182). |
| `StallReport.h` | Where the tests are when a test case takes too long: with `PHAZITE_TEST_STALL_SECONDS` set, its name and (on Windows) the tests' thread's stack, written every so many seconds, for a test file that reaches ctest's limit in CI. |
| `TestHelpers.h` | The shared includes and helpers; every test file includes it: among them `RenderHost` (runs freezes, bounces and the progress windows of work the window holds for, a first save's copy among them, as the main window does, letting go of the render before it uses what the render said) and `linkFolder()` (a junction on Windows, a symbolic link elsewhere); and `hangTimeout`, how long `runTimersUntil()` and `dispatchMessagesUntil()` wait for a condition unless told otherwise: two minutes, which only a hang reaches; and `HeldClock`, which holds still the clock Phazite reads its timeouts and the CPU meters' and the engine's times by (`src/devices/core/Clock.h`), moved on only by the test. |
| `TestSong.h` | A project in a temporary folder, open in a project context of its own, with the app's commands, for building a song through the model as the UI does; its automation is written in the parameter's own units (hertz, a pan from -1 to 1), each value put where its control would be, as a point keeps it (`addAutomation()`). `finished()` runs a command of the versions that reads whole songs on the history's thread first (a switch, a merge's list, a restore) and waits until what it read is taken in; `withChangesIn()` waits until the changes since the last version, worked out on the history's thread, are the song's as it is (`getChangesSinceLastVersion (withChangesIn (context))`); a plug-in it adds is waited for as it loads in the background (`waitForPlugins()`). `VersionsTime` sets the versions' clock while it lives (`getVersionsTime()`), and lets the store's sweep leave out however few bytes, so that a test lets days pass for the 30 days the versions keep what left every branch, and for the sweep; `openEachWeek()` opens the project once a week of them, as the sweep keeps by a week past its last at most; `SweepLetsGo` turns on, while it lives, the sweep's letting go of what nothing names and each computer's copy of what its history names, off in the product (`StoreSweep.h`: `doesSweepLetGo()`), so that they stay tested (`VersionsRecoveryTests.cpp`, `VersionsSweepTests.cpp`, `VersionsTwoComputersTests.cpp`). |

| `TestTracks.h` | Tracks and the master read by the song and IDs, never by the live song's elements of them, as the tracks move beside the song's tree (roadmap step S5.20; the helpers' bodies are what its pieces change): what the song holds of a track (the master's for its ID) as its element written whole (`copyTrack()`, a copy, for reading a property or its lanes; `getTrackProperty()` for one property), whether the song holds a track (`hasTrack()`), a track's element in a whole copy by its ID (`findTrackIn()`), whether the live tree holds an element of a type anywhere (`treeHolds()`, for a test that checks it holds no clip). A song that holds what no model function makes opens from a whole copy whose track's element is changed by hand (`findTrackIn()`, then `makeSong()`). What a test sets of a track (a name, a volume, a height, a mute, a lane) it sets through the model's functions by ID. |
| `SongIDs.h` | A song's IDs checked: every item's once in the song, a note's once in its clip, and what names an item naming one the song has; with the known exceptions of a song being edited (known bugs 102 and 143). |
| `SongCheck.h` | `checkSong()` and `findSongProblems()`: a song checked for consistency, as any song Phazite loads must be, by the places, ranges, words and hexadecimal ids `Schema.h` describes (read from the description, as the loader reads them) and other rules written apart from the loader's code (place, id, names, key, kind, range, path, alias: the clips of an alias group hold the same notes and values, are of one kind and are two at least; values: of a song that holds its clips' notes as values beside its tree, no clip in the tree holds a NOTE or CONTROL element, every MIDI clip has a value and no value is a clip's that isn't there, and an alias group's clips hold ONE value, which `findValueProblems()` and `checkValues()` check alone of a song an edit left). | `RandomEdits.h` | Songs made by edits drawn from a seed, through the model, of over 60 kinds (tracks, buses, devices, containers, sidechains, pads' tracks, clips, automation, modulation, sections, chords, tempo...; every edit of notes and controllers' values of `Notes.h`, and clips split, duplicated, copied as aliases, deleted, made unique, moved and trimmed one by one, on clips of alias groups half of the time): the same seed makes the same song with every compiler. |
| `Fuzzer.h` | The mutation fuzzer: valid files damaged in many ways (bytes, and XML's and JSON's structure), each round from the case's seed, a failure printed with its seed and round and its input written into the golden tests' actual folder. |
| `PerformanceCounts.h` | Counts of work that don't depend on the machine: `PlanCounter`, the plans a project gives the engine, and `countAllocations()`, the allocations a piece of work makes (where `AudioThreadMonitor.h` counts them). |
| `BenchmarkSong.h` | `buildBenchmarkSong()`: a busy song of any number of tracks, every one playing all the way through, for the 100-track benchmark, the gates and the long run; `timeEngineBlocks()` times the engine's blocks on the calling thread. |
| `ProcessMemory.h` | The test process's memory from the operating system, for the long run. |
| `PaintCheck.h` | `paintComponent()` and `checkPaints()`: a component painted with its children by JUCE's software renderer at an interface scale, and checked to finish, raise no assertion and draw something. No picture is kept. |
| `UiTestHelpers.h` | For tests of components: a `TestWindow` that isn't on any screen (it works headless, as on Linux CI), through which a `Mouse` and `pressKey()` reach the components the way JUCE delivers real events, mouse and key listeners included, and which says what was asked to repaint (`takeRepaintedArea()`); `dispatchPendingMessages()` delivers every message posted before the call and what those post in turn; `dispatchMessagesUntil()` waits for the effect of a message another thread posts; `createHeadlessPeer()` puts a window the app makes (the main window, a dialog) on no screen as well; `isMenuShownAt()` says whether the menu a press showed has a corner at the pointer, as a right-click's menu should. |
| `AppScreen.h` | The main window's content built as the app builds it, in a `TestWindow`, for tests and benchmarks that need the whole window; `showView<View>()` shows a view by its command, `addEveryOwnDevice()` adds a track for each of Phazite's own devices, and `showInDevicesView()` shows one in the Devices view. |
| `EnginePlayback.h` | Phazite's engine playing the open project, driven a block at a time, the same every time; `Timing::asRender` for comparing what plug-ins in helpers play, whose blocks otherwise keep a deadline in real time. |
| `RenderHarness.h` | A song rendered offline through Phazite's engine, always the same way; its fingerprint (the RMS and peak level of each 100 ms block on each side), compared with a golden one or another render's. |
| `GoldenFiles.h` | Golden files: what Phazite makes, compared with the files committed in `golden/`, each difference listed. |
| `TestDevices.h` | Devices of the tests' own that Phazite's engine plays as its own: a gain (and one with a sidechain it never hears, for a sidechain set through the model), an instrument that plays its notes' velocity, a delay with latency, an effect of any latency (Test Latency, for delay compensation), an effect that plays its sidechain. |
| `TestKeyboardLayouts.h` | Keyboard layouts for tests: the US layout, French AZERTY, German QWERTZ, Czech, Spanish and Swedish, as what each types at the keys' places, with their dead keys and the keys held; `ShortcutTests.cpp` walks each one's keys to find a key for every command of each keymap. |
| `TestPlugin.h` | The stand-in for a plug-in (a VST3): the effect of `host/TestPlugins.h`, in versions as an update makes them, which loads in the tests' helper as every plug-in does. |
| `SandboxedPlugins.h` | While one lives, the test engine knows the tests' stand-ins as if a scan had found them, each loading into the tests' helper, which is taken for hung only after `hangTimeout` (a hang's test sets the short limits itself: `useShortHangLimits()`). |
| `TestAudioDevice.h` | An audio device of a type of its own on JUCE's device manager, its blocks played when a test asks, and a sample rate it refuses, for a device that doesn't open. |
| `HostedDevice.h` | The tests' audio device opened as the app opens one, for tests and benchmarks that process blocks themselves on a thread of their own; `playLiveNote()` plays a live note between two blocks and measures it by the engine's clock: where the engine plays it and when it sounds, and where it took it to have come against the wall clock read on both sides, which no load on the machine moves. |
| `RealTimePlayback.h` | Playing in real time through the tests' audio device, for tests that need an audio device with inputs. |
| `AudioThreadMonitor.h` | Counts allocations and frees on audio threads (one the test marks, and the engine's workers), for the real-time audit: in Windows Debug builds and Linux builds with glibc, with each one's call stack; under Linux's sanitizers, without. | `MotionTestHelpers.h` | What Motion's tests share (`MotionTests.cpp`, Motion itself; `MotionEffectTests.cpp` and `ChorusTests.cpp`, its engines' DSP): an effect played through its runner, and a tone read in what comes out. |
| `SoundPackTestHelpers.h` | A small Phazite Sounds pack and a release that pins it. |
| `HeldFile.h` | A file nobody else can read, write, replace or delete while one lives (on Windows held open with no sharing; elsewhere its permissions taken away), for tests of what fails when a file can't be reached. |

## host/

The tests' helper program, `phazite_test_host`, which every plug-in in the tests loads in (its path is
`PHAZITE_TEST_HOST`): it hosts VST3s and the stand-ins of `host/TestPlugins.h`, a format of their own, "Test"
(`host/TestFormats.cpp`), among them a slow one (held by a gate as it is made, gives its state, writes or reads a value's
text, makes its editor, or goes), shell files that hold a thousand plug-ins and more than Phazite takes from a file, and
one that tells nonsense (values that are no number, texts of any length, two
parameter IDs that are the same once cut to 128 characters). `host/SandboxTestHelpers.h`
opens the stand-ins in a helper and plays blocks through them;
`host/ThreadCpu.h` gives a thread's CPU time for the benchmarks.
