# tests

Phazite's tests, in the `phazite_tests` target, which links `phazite_app` and `phazite_ui` and is written with doctest
(MIT, `external/doctest`, compiled into the tests only, as a system include with its warnings off). Each `*Tests.cpp` file holds the tests of one area; `ctest --preset <preset>` runs the
executable once for each test file. The rules for writing tests are in `CLAUDE.md`, "Tests".

## Helpers

| File | What it gives a test |
|---|---|
| `TestMain.cpp` | The test runner: doctest inside a JUCE environment. On Windows it ends the program once every static object has gone (JUCE's leak detector has checked each class), with main()'s result, without the C runtime's teardown, during which a thread the graphics driver started once crashed it (known bug 182). |
| `StallReport.h` | Where the tests are when a test case takes too long: with `PHAZITE_TEST_STALL_SECONDS` set, its name and (on Windows) the tests' thread's stack, written every so many seconds, for a test file that reaches ctest's limit in CI. |
| `TestHelpers.h` | The shared includes and helpers; every test file includes it: among them `RenderHost` (runs freezes, bounces and the progress windows of work the window holds for, a first save's copy among them, as the main window does, letting go of the render before it uses what the render said) and `linkFolder()` (a junction on Windows, a symbolic link elsewhere); and `hangTimeout`, how long `runTimersUntil()` and `dispatchMessagesUntil()` wait for a condition unless told otherwise: two minutes, which only a hang reaches; and `HeldClock`, which holds still the clock Phazite reads its timeouts and the CPU meters' and the engine's times by (`src/devices/core/Clock.h`), moved on only by the test. |
| `TestSong.h` | A project in a temporary folder, open in a project context of its own, with the app's commands, for building a song through the model as the UI does; its automation is written in the parameter's own units (hertz, a pan from -1 to 1), each value put where its control would be, as a point keeps it (`addAutomation()`). `finished()` runs a command of the versions that reads whole songs on the history's thread first (a switch, a merge's list, a restore) and waits until what it read is taken in; `withChangesIn()` waits until the changes since the last version, worked out on the history's thread, are the song's as it is (`getChangesSinceLastVersion (withChangesIn (context))`); a plug-in it adds is waited for as it loads in the background (`waitForPlugins()`). `VersionsTime` sets the versions' clock while it lives (`getVersionsTime()`), and lets the store's sweep leave out however few bytes, so that a test lets days pass for the 30 days the versions keep what left every branch, and for the sweep; `openEachWeek()` opens the project once a week of them, as the sweep keeps by a week past its last at most; `SweepLetsGo` turns on, while it lives, the sweep's letting go of what nothing names and each computer's copy of what its history names, off in the product (`StoreSweep.h`: `doesSweepLetGo()`), so that they stay tested (`VersionsRecoveryTests.cpp`, `VersionsSweepTests.cpp`, `VersionsTwoComputersTests.cpp`). |
| `TestClips.h` | MIDI clips, audio clips and notes made through the model, by the song and IDs, for a song made without a project (`phazite::createSong()`). |
| `SongIDs.h` | A song's IDs checked: every item's once in the song, a note's once in its clip, and what names an item naming one the song has; with the known exceptions of a song being edited (known bugs 102 and 143). |
| `SongCheck.h` | `checkSong()` and `findSongProblems()`: a song checked for consistency, as any song Phazite loads must be, by rules written from `Schema.h`'s comments, apart from the loader's code (place, id, names, key, kind, range, path). |
| `RepresentativeSong.h` | `addRepresentativeSong()`: one of each kind of track and every piece of data a project keeps, which the golden project saves and the whole window's tests show, walk and paint. |
| `RandomEdits.h` | Songs made by edits drawn from a seed, through the model, of 30 kinds (tracks, buses, devices, containers, sidechains, pads' tracks, clips, notes, automation, modulation, sections, chords, tempo...): the same seed makes the same song with every compiler. |
| `Fuzzer.h` | The mutation fuzzer: valid files damaged in many ways (bytes, and XML's and JSON's structure), each round from the case's seed, a failure printed with its seed and round and its input written into the golden tests' actual folder. |
| `PerformanceCounts.h` | Counts of work that don't depend on the machine: `PlanCounter`, the plans a project gives the engine, and `countAllocations()`, the allocations a piece of work makes (where `AudioThreadMonitor.h` counts them). |
| `BenchmarkSong.h` | `buildBenchmarkSong()`: a busy song of any number of tracks, every one playing all the way through, for the 100-track benchmark, the gates and the long run; `timeEngineBlocks()` times the engine's blocks on the calling thread. |
| `ProcessMemory.h` | The test process's memory from the operating system, for the long run. |
| `PaintCheck.h` | `paintComponent()` and `checkPaints()`: a component painted with its children by JUCE's software renderer at an interface scale, and checked to finish, raise no assertion and draw something. No picture is kept. |
| `UiTestHelpers.h` | For tests of components: a `TestWindow` that isn't on any screen (it works headless, as on Linux CI), through which a `Mouse` and `pressKey()` reach the components the way JUCE delivers real events, mouse and key listeners included, and which says what was asked to repaint (`takeRepaintedArea()`); `dispatchPendingMessages()` delivers every message posted before the call and what those post in turn; `dispatchMessagesUntil()` waits for the effect of a message another thread posts; `createHeadlessPeer()` puts a window the app makes (the main window, a dialog) on no screen as well. |
| `AppScreen.h` | The main window's content built as the app builds it, in a `TestWindow`, for tests and benchmarks that need the whole window; `showView<View>()` shows a view by its command, `addEveryOwnDevice()` adds a track for each of Phazite's own devices, and `showInDevicesView()` shows one in the Devices view. |
| `EnginePlayback.h` | Phazite's engine playing the open project, driven a block at a time, the same every time; `Timing::asRender` for comparing what plug-ins in helpers play, whose blocks otherwise keep a deadline in real time. |
| `RenderHarness.h` | A song rendered offline through Phazite's engine, always the same way; its fingerprint (the RMS and peak level of each 100 ms block on each side), compared with a golden one or another render's. |
| `GoldenFiles.h` | Golden files: what Phazite makes, compared with the files committed in `golden/`, each difference listed. |
| `TestDevices.h` | Devices of the tests' own that Phazite's engine plays as its own: a gain, an instrument that plays its notes' velocity, a delay with latency, an effect of any latency (Test Latency, for delay compensation), an effect that plays its sidechain. |
| `TestKeyboardLayouts.h` | Keyboard layouts for tests: the US layout, French AZERTY, German QWERTZ, Czech, Spanish and Swedish, as what each types at the keys' places, with their dead keys and the keys held; `ShortcutTests.cpp` walks each one's keys to find a key for every command of each keymap. |
| `TestPlugin.h` | The stand-in for a plug-in (a VST3): the effect of `host/TestPlugins.h`, in versions as an update makes them, which loads in the tests' helper as every plug-in does. |
| `SandboxedPlugins.h` | While one lives, the test engine knows the tests' stand-ins as if a scan had found them, each loading into the tests' helper, which is taken for hung only after `hangTimeout` (a hang's test sets the short limits itself: `useShortHangLimits()`). |
| `TestAudioDevice.h` | An audio device of a type of its own on JUCE's device manager, its blocks played when a test asks. |
| `HostedDevice.h` | The tests' audio device opened as the app opens one, for tests and benchmarks that process blocks themselves on a thread of their own; `playLiveNote()` plays a live note between two blocks and measures it by the engine's clock: where the engine plays it and when it sounds, and where it took it to have come against the wall clock read on both sides, which no load on the machine moves. |
| `RealTimePlayback.h` | Playing in real time through the tests' audio device, for tests that need an audio device with inputs. |
| `AudioThreadMonitor.h` | Counts allocations and frees on audio threads (one the test marks, and the engine's workers), for the real-time audit: in Windows Debug builds and Linux builds with glibc, with each one's call stack; under Linux's sanitizers, without. It also says which threads play audio (`isAudioThread()`: those, and a block of the tests' audio device), and which of its events JUCE made for an assertion's message (`ofAssertions()`). |
| `MotionTestHelpers.h` | What Motion's tests share (`MotionTests.cpp`, Motion itself; `MotionEffectTests.cpp` and `ChorusTests.cpp`, its engines' DSP): an effect played through its runner, and a tone read in what comes out. |
| `SoundPackTestHelpers.h` | A small Phazite Sounds pack and a release that pins it. |
| `HeldFile.h` | A file nobody else can read, write, replace or delete while one lives (on Windows held open with no sharing; elsewhere its permissions taken away), for tests of what fails when a file can't be reached. |

## The nets

What a change must keep true, and where each net is:

| Net | Where | What a change does |
| --- | --- | --- |

| Every command is run | `CommandGoldenTests.cpp`: the script runs every model command where it changes something, each through an `UndoCheck` | Run a new command in the script, or list it in `getCommandsNotRun()` with why |

| Playback at every condition | `PlaybackConditions.h`: five pairs of rate, block size and tempo (`atEveryCondition()`), with the engine's own invariants in `PlaybackConditionTests.cpp` | Wrap a test of anything playback promises everywhere in `atEveryCondition()` |
| Live playback as the render | `RenderHarness.h`: `checkGoldenRender()` renders a golden song, renders a copy and plays it live, and all three must match; what only live playback plays is a golden through `checkGoldenAudio()` (`GoldenLiveTests.cpp`) | A song that can't match live passes a `liveDiffers` reason |
| Fingerprints | `RenderHarness.h`: for each 100 ms, each side's RMS and peak, ten band levels, the RMS frequency and where the power lies | They don't see phase, a steady sound a few samples late, or a pitch change under a tenth of a semitone |
| Every device keeps the rules | `DeviceConformanceTests.cpp` runs every device of `getOwnDevices()` at 44.1, 48 and 96 kHz (Motion once in each of its modes and Age in each of its media, its `variants`): numbers, nothing (playing and stopped, from `prepare()` and after a `reset()`), tail, latency, mix, blocks, automated blocks, starting over, offset | A new device is picked up by itself; one that can't keep a rule gets a line in the `exceptions` table with its reason, and the test fails once the exception isn't needed |
| A JUCE assertion fails its test | `TestMain.cpp`: in Debug builds an assertion that fires during a test case fails it, with its file, line and stack; one outside a case, or as the program ends (leaked objects), fails the run. On an audio thread the net neither locks nor allocates: it notes the place in a slot made before, and the tests' thread fails the test case with it, at its next check (no stack: a debugger stops there, and the real-time audit lists what JUCE allocated for its message, which it leaves out of its counts) | Fix what raises it, or list it in `allowedAssertions` with JUCE's file and line and why (today: what a Linux machine without a display or MIDI lacks, T7 in `docs/juce-workarounds.md`); a test that makes the fault on purpose declares it with `ExpectedAssertion` (`TestHelpers.h`), around what makes it and nothing else (one made while another lives adds its places for as long as it lives: the DAWproject fuzz case's zip dates, T8). A place is the file's name and its line, or its first and last line for an assertion written over several (`juce_Time.cpp:170-175`): compilers differ in which they give |
| Nothing allocates on the audio thread, edited or not | `RealtimeAuditTests.cpp`: every block counts unless a scenario names warm-up blocks with a reason; a scenario's `Edit`s run on the message thread at set blocks while the song plays | Add an `Edit` to a scenario for an edit that could reach the audio thread |
| Real time without the wall clock | `RealTimePlayback.h`: `waitForBlocks()` and `blocksFor()` wait for audio played; `HostedDevice.h`: `playLiveNote()`, a live note measured by the engine's clock; `TestHelpers.h`: `hangTimeout`, the limit of a wait for a condition, and `HeldClock`, the clock of Phazite's timeouts held still (`src/devices/core/Clock.h`: the Listen keys, the auditions' window, a meter's peak hold, a burst of typing, the tempo panel, Auto Save's waits, the CPU meters, the engine's block times and playhead stamps) | A test never waits for a time: what the message thread does is `dispatchPendingMessages()` ("the engine has the song" too: it compiles and hands over the plan), what another thread does is a condition (`dispatchMessagesUntil()`, `runTimersUntil()`) with the default limit, `hangTimeout`, as every limit a helper or a call takes; a timeout Phazite reads from `devices::Clock` is tested with the clock held, ticked (`tickNow()`) just short of the timeout and just past it; times compared with the engine's (frames, live notes) are read from `devices::Clock`. The wall clock is left for these kinds alone: a lower bound (at least so long has passed, a sleep marked "a lower bound only"); an absence (nothing happens while JUCE's timers run for a stretch, which a busy machine can only make miss, never fail, marked "an absence"); a quiet stretch looked for within `hangTimeout`; time itself as the subject (a drag's auto-repeat timers, JUCE's: `settle()`, `GoldenFiles.h`, says so); printing how long something took; and the benchmarks and the long run, which ctest doesn't run. `VersionsHearingTests`, which measures call lengths, runs alone in ctest |
| The lock-free parts raced | `LockFreeTests.cpp`: the live notes' queue, the handover (with what the audio thread keeps playing past it), the engine given and dropping plans that realign as it plays, a delay's ring taking what the one before held (and the delay what the one it took the place of played), the playhead's stamps, the transport, a device's sample tap, and the synth's and the sampler's sounds let go of as they are swapped, each raced on real threads for a fixed count of operations | Meaningful under ThreadSanitizer (`linux-tsan`); a new lock-free part gets a race there |
| A real VST3 | `vst3/TestVst3s.h`: a mono effect (gain, invert, 100 samples of latency, programs) and a stereo instrument with an input bus, built by `juce_add_plugin` for the tests only; `Vst3PluginTests.cpp` scans and loads them through the tests' helper as a user's plug-in | Their paths are `PHAZITE_TEST_VST3_EFFECT` and `PHAZITE_TEST_VST3_SYNTH` |
| The editors' tools and drags | `EditorScreens.h`: `PlaylistScreen` and `PianoRollScreen`, an editor in a `TestWindow` with the app's commands and keys; `EditorToolTests.cpp` drives every tool with the mouse, `EditorDragTests.cpp` changes the song between a press and its release; `GraphDragTests.cpp` drags the devices' graphs (a press at a handle's edge changes nothing, a modulated parameter's value set by hand moves by the drag alone, Escape takes a drag back in every graph and on a knob's ring) | Name items through the model by IDs, and call `deliverChanges()` after each gesture; a new graph's drag goes through `graph::HandleDrag` and gets a case in `GraphDragTests.cpp` |

| Measuring a device | `DspProbe.h`: signals, measurements and `probe::Device`, the device on its runner as the engine plays it | New device tests use it instead of their own `play()` and DFT helpers; `PHAZITE_DEVICE_REPORT=1` prints what each rule measured |
| Every reader refuses a damaged file or reads it into something that holds together | `FuzzTests.cpp`, on `Fuzzer.h`, in every ctest run: project files, a version's pieces, packs and records, presets, DAWproject archives, `.vstpreset` states, the helper's messages, the settings and the library's facts file, keymaps and audio files' headers, each seeded from real files; none may crash, hang or assert | A new reader of files gets a case there. `PHAZITE_FUZZ_ROUNDS` sets each case's rounds (the nightly run: 20000), `PHAZITE_FUZZ_ROUND` runs again the one round that failed |
| A loaded song holds together | `SongCheck.h`: `checkSong()` states the song's rules a second time, apart from the loader; `InconsistentProjectTests.cpp` opens projects that parse but don't hold together, which `makeConsistent()` must repair or refuse | A test that loads a song checks it with `checkSong()`; a new saved value with a range states it in `Schema.h`, then in the loader's table (`getRanges()`, `src/model/project/Project.cpp`) and in `SongCheck.cpp`'s |

## host/

The tests' helper program, `phazite_test_host`, which every plug-in in the tests loads in (its path is
`PHAZITE_TEST_HOST`): it hosts VST3s and the stand-ins of `host/TestPlugins.h`, a format of their own, "Test"
(`host/TestFormats.cpp`), among them a slow one (held by a gate as it is made, gives its state, writes or reads a value's
text, makes its editor, or goes), shell files that hold a thousand plug-ins and more than Phazite takes from a file, and
one that tells nonsense (values that are no number, texts of any length, two
parameter IDs that are the same once cut to 128 characters). `host/SandboxTestHelpers.h`
opens the stand-ins in a helper and plays blocks through them;
`host/ThreadCpu.h` gives a thread's CPU time for the benchmarks.

## Golden tests

The golden tests (`--test-suite=golden`: `*Golden*.cpp` and the catalogue case in `AppShellTests.cpp`) compare with
files committed in `golden/`:

| Folder | What is compared |
|---|---|
| `golden/projects/` | What Phazite saves. |
| `golden/renders/` | What it plays: level fingerprints of offline renders, never audio, of songs made with `TestSong.h` that show everything that plays, each rendered through Phazite's engine, of the open project and of a copy of its song alone, and checked before it is compared, with `RenderHarness.h`. |
| `golden/commands/` | The model's commands: ids, texts, switches and order; a script that runs each of them, with the saved result, the undo step each makes, and every command's enabled, ticked and name state along the way; and every command the app registers, in order, with its keys (`app-catalogue.txt`). |
| `golden/format/` | The formats' test vectors: the song's rules, every device's parameters, and a pack with what it holds ([docs/project-format.md](../docs/project-format.md), [docs/versions-format.md](../docs/versions-format.md)). |
| `resources/presets/` | The presets that come with Phazite, each as Save Preset writes it (the golden case in `FactoryPresetTests.cpp`). |

`ScrollingFrameTests.cpp` checks what the playlist and the piano roll show from frame to frame while they follow the
playhead, by painting frames as the window does, by each renderer Phazite's windows paint with (Direct2D, and the
software renderer that Linux's use): nothing beside the time line changes, everything on it moves as far as the song
played, and what stays in view stays put.
