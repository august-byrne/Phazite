# JUCE workarounds

*JUCE 9.0.5; listed on 2026-11-11.* Phazite builds on JUCE, and most of its JUCE code uses JUCE as JUCE means it to be used. Some of it is there only because JUCE does something wrong, lacks something or keeps something to itself, or it leans on something JUCE doesn't promise. This list keeps the two apart:

- **Workarounds:** code that would go, or be simpler, if JUCE changed: W in the code, B in the build, T in the tests' harness. Each is marked where it is with `JUCE workaround <number> (docs/juce-workarounds.md)`, so `git grep "JUCE workaround"` finds every one. Those marked *JUCE's insides* lean on something JUCE doesn't document (a format of its own, a message's number, a name), which an update can change without a word.
- **Correct patterns:** code shaped by JUCE that looks like a workaround but uses JUCE as documented. It isn't marked, and an update needs nothing of it. Don't "fix" it.
- **Open questions:** code whose reason isn't settled yet, each with what decides it.

How to keep it:
- Code that works around JUCE gets an entry here and the marker in its comment, in the same change; code that stops working around it loses both. A number isn't used again.
- At each JUCE update (CLAUDE.md, "Submodules and third-party code"), go through the workarounds: look at what each names in the new JUCE, remove those it fixed, and check that the insides the code leans on are still as it expects.
- JUCE's files are named by their path in `external/JUCE/modules/`, or in `external/JUCE/` for its build scripts.

## Workarounds

### Threads

**W1. No thread is ended by force.** `juce::Thread::stopThread()` with a time limit ends a thread that hasn't stopped in time, with `TerminateThread()` on Windows (`juce_core/threads/juce_Thread.cpp`, `juce_core/native/juce_Threads_windows.cpp`), which can leave a lock the thread held held for ever: a loader lock left so hung every thread started after it (2026-11-10). `juce::ThreadPool` does it to a thread that hasn't stopped within half a second (`juce_core/threads/juce_ThreadPool.cpp`), and a `TimeSliceThread` as it goes, after 2 s (`juce_TimeSliceThread.cpp`). So Phazite runs its jobs on `phazite::BackgroundJobs` (`src/model/base/BackgroundJobs.h`), stops each `AudioThumbnailCache`'s thread itself first (`src/app/ClipWaveforms.cpp`, `src/ui/browser/SoundView.cpp`), and cancels a plug-in scan before JUCE's plug-in list waits for its pool (`src/app/MainWindow.cpp`, `PluginList`, and `juce_audio_processors/scanning/juce_PluginListComponent.cpp`). `tools/check-architecture.sh` counts the rest (`thread-kills`). `stopThread (-1)` itself is JUCE's documented wait without a limit, a correct pattern.

**W2. The audio threads' priority on Windows.** A real-time thread of JUCE's on Windows puts the whole process in the real-time priority class, or the high one (`Process::setPriority()`, `juce_core/native/juce_Threads_windows.cpp`), every thread of the app above other programs'. Phazite's threads that play audio, the engine's workers and the helpers' threads that play plug-ins, take the highest priority and join MMCSS's "Pro Audio" task, as JUCE's own WASAPI thread does (`src/devices/core/AudioThreads.*`); `tests/EngineTests.cpp` checks that the process's class stays as it was. Elsewhere they are JUCE's real-time threads.

**W61. A thread left to end by itself is not one of `juce::Thread::launch()`'s.** JUCE's launched thread deletes itself as it ends (`deleteOnThreadEnd`, `juce_core/threads/juce_Thread.cpp`), and `Thread::startThread()` holds the thread's own lock until it returns, so a job that ends at once (one told to stop before it began) has the thread, and its lock, destroyed while the starter still holds it: ThreadSanitizer reported the lock unlocked after it was destroyed (CI, 2026-11-20). The work Phazite leaves behind rather than wait for, which may be inside the system for as long as a drive takes to answer (the browser's index walk, the Project view's check for missing files), runs on a plain thread that is let go as it starts (`phazite::runLeftBehind()`, `src/model/base/BackgroundJobs.h`), at the normal priority, since only a `juce::Thread` takes one of JUCE's.

### Plug-ins

**W3. A VST3's restartComponent() isn't taken for a new program.** JUCE's VST3 host reports every `restartComponent()` a plug-in makes as a program change with new parameter info, whatever the plug-in's flags said (`restartComponentOnMessageThread()`, `juce_audio_processors_headless/format_types/juce_VST3PluginFormatImpl.h`), and many make one as they sit there, for their latency or their parameters' names. The helper counts a program change without new parameter info, and one with it only where the program's number changed from the one Phazite last knew of (a MIDI program change; `src/host/core/Instance.cpp`); counting them all made an idle project's plug-ins an unsaved change. A plug-in that loads a preset with nothing but `restartComponent()`, no `setDirty()`, counts only as its values change. It goes when JUCE passes the plug-in's own flags on.

**W4. A VST3's state as JUCE's own block (*JUCE's insides*).** The song keeps a VST3's state as the format's own preset file (`.vstpreset`), but the helper gives it to the plug-in and reads it back through `setStateInformation()` and `getStateInformation()`, turned to and from the block JUCE writes there, a `VST3PluginState` element through `copyXmlToBinary()` (`src/sandbox/core/Vst3State.h`, `src/host/core/Instance.*`): JUCE's `setPreset()` loads a preset without setting the parameters' values again, and `getPreset()` doesn't flush them first, as the state's calls do (`juce_VST3PluginFormatImpl.h`). A plug-in's class ID comes from the header of what `getPreset()` writes, as JUCE has no call for it. `tests/Vst3StateTests.cpp` checks the block's format. It goes when JUCE's preset calls do what its state calls do.

**W5. A helper that crashes is noticed by a thread that watches it.** On Windows, when the helper at the other end goes, JUCE's named pipe waits for another to connect rather than failing (`NamedPipe`, `juce_core/native/juce_Files_windows.cpp`), and `InterprocessConnection` takes a read that times out for a lost connection (`juce_events/interprocess/juce_InterprocessConnection.cpp`). So the pipe has no time limit (JUCE's -1), a thread of Phazite's looks at the helper's process five times a second, and closing the pipe wakes a read or a write waiting on it (`src/sandbox/client/Helper.*`, `src/host/core/Host.cpp`). The watching thread also finds helpers that hang, which stays whatever JUCE does; only the crashes' part would go.

**W6. A plug-in scan keeps when unchanged plug-ins were described.** JUCE's formats stamp every plug-in they describe with the time of the scan, changed or not (`lastInfoUpdateTime`, `juce_VST3PluginFormatImpl.h` and the other formats). The scan gives a plug-in whose file and version are the same the time it had (`keepUpdateTimesOfUnchanged()`, `src/model/engine/PluginScanner.cpp`).

**W28. Phazite's own helper processes, not JUCE's `ChildProcessCoordinator`.** JUCE's coordinator keeps its `ChildProcess` to itself and ends a worker only by asking it to quit (`killWorkerProcess()`, `juce_events/interprocess/juce_ConnectedChildProcess.cpp`), so a helper that hangs couldn't be ended; it notices a crash only when its pings stop, after its time limit (8 s unless told otherwise), not within a fifth of a second; its pings are answered on the pipe's thread, so a helper whose message thread hangs looks alive; its worker ends itself when Phazite's pings stop, as they do while Phazite is paused in a debugger; and it stops its ping thread with a time limit of 10 s (W1). So Phazite starts and talks to its helpers with JUCE's own parts, `ChildProcess` and `InterprocessConnection`, with the coordinator's command line (`--<name>:<pipe>`), and adds what is missing (`src/sandbox/client/Helper.*`; the helper's side, `src/host/core/Host.cpp`). The owner asked for the switch to JUCE's coordinator if nothing would be lost (2026-11-11); this much would be.

**W31. A helper's errors written to a copy of Phazite's stderr, in a build with a sanitizer (Linux and macOS).** JUCE's `ChildProcess` either reads what the helper writes to stderr through a pipe or sends it nowhere (`juce_core/native/juce_SharedCode_posix.h`); a reader of that pipe waits until every process holding it has gone, so a plug-in that started a process of its own kept closing its helper waiting. Built with a sanitizer, Phazite gives the helper a copy of its own stderr, which the helper inherits because JUCE's POSIX `ChildProcess` doesn't close a parent's descriptors on exec (a behaviour JUCE doesn't promise), and names it on the command line (`--PhaziteSandboxErrors:<descriptor>`); the helper writes its stderr there as it starts (`src/sandbox/client/Helper.cpp`, `writeErrorsTo()` in `src/host/core/Platform.cpp`). It would go if `ChildProcess` could hand a child the parent's stderr.

**W32. A helper's process ID told in its hello.** `juce::ChildProcess` keeps its process handle and ID to itself, so Phazite can't put the helper in its job on Windows (which ends the helpers as Phazite ends, however it ends). The helper tells its own ID in its answer to the hello (`MessageType::hello`, `src/host/core/Host.cpp`), and Phazite opens the process by it and puts it in the job (`src/sandbox/client/Helper.cpp`). It would go if `ChildProcess` gave its process's ID or handle.

**W50. The keys a plug-in's editor doesn't take, posted on by the socket it is in.** JUCE's window for a component added to the desktop inside another program's window posts the key messages its components don't take to its parent (`forwardMessageToParent()`, `juce_gui_basics/native/juce_Windowing_windows.cpp`), which is how a key pressed over a plug-in reaches the host. The helper's window for a plug-in's editor is in a socket window of Phazite's own (`src/app/SandboxedEditor.cpp`, known bug 165), whose procedure posts those messages on to its own parent, Phazite's window, which then takes them as it did when the helper's window was its child. It would go if the socket were a JUCE window that took them, or JUCE's child window told Phazite another way.

**W51. The helper's window for a plug-in's editor tells Phazite's nothing of what happens in it.** JUCE has no option for a window's `WS_EX_NOPARENTNOTIFY`, which keeps Windows from sending its parent (Phazite's, another process's) `WM_PARENTNOTIFY` as the window is clicked or destroyed, and waiting for Phazite's thread to take it. The helper sets the style on its JUCE window as it adds it to Phazite's (`Editor::Holder::place()`, `src/host/core/Editor.cpp`), and again each time it adds it to another (JUCE makes its native window anew only in `addToDesktop()`, which is that place alone). It would go if JUCE's `ComponentPeer` style flags had one for it.

**W52. On Linux, the helper's window for a plug-in's editor is in an X window of Phazite's own, taken out before JUCE's window can go.** X destroys every window inside one that is destroyed, the helper's too, and JUCE says nothing before it destroys its window (a window closed, or made again as a peer is): the helper's window was destroyed under the helper, so Phazite waited up to 2 seconds for the helper to take it out first (known bug 166). `src/app/SandboxedEditor.cpp` puts the helper's window in a socket, a plain X window of Phazite's own made through its own display (W53), which it moves into the root window, unmapped, as soon as the editor stops showing or goes, and destroys once the helper's window has left it or the helper has gone. What it can't cover: when JUCE destroys or makes again the window the editor is in before the editor hears of it (componentPeerChanged() comes after X has destroyed the socket with all in it: a peer made again by setAlwaysOnTop(), setUsingNativeTitleBar() or a change of the window's style flags, or a window deleted with the editor still in it), the helper's window goes with it and the editor shows blank until the window is opened again; Phazite's plug-in windows do none of these while an editor is in them, but nothing stops a later change doing it (known bug, see docs/known-bugs.md). JUCE can't tell a component's window it is about to be destroyed, nor take a foreign child out of it first. It would go if JUCE's Linux peers did either, or if JUCE's X display could be used outside JUCE. Not compiled or run on Windows, where it was written: CI's Linux builds are its first compile.

**W53. A private X display for the sockets, with its own error handler around their requests.** JUCE's X display is its own (`XWindowSystem`, not part of its API), so the sockets (W52) are made through a display of Phazite's own, opened through libX11 loaded at run time as JUCE loads it (with `dlopen()` itself: a `juce::DynamicLibrary` never destroyed is a leak to JUCE's leak detector, which fails a Debug build's tests as they end), never closed (closed as static objects go, after JUCE has taken its error handler away, an error still to come would reach Xlib's default handler, which ends the process). Each request that can meet a window that died (reparenting, unmapping, destroying, asking what a window holds) is made with an error handler of its own installed, until `XSync()` has had the X server's answers, then the handler before is put back, as JUCE does around its own. It would go if JUCE's display were public.

**W33. Two steps make a switch.** JUCE's VST3 host describes a VST3's switch (a parameter with one step) as a parameter of two steps, never as a switch: its parameter doesn't override `isBoolean()` (`juce_audio_processors_headless/format_types/juce_VST3PluginFormatImpl.h`). The helper takes a parameter of exactly two steps for a switch, its two values keeping the plug-in's own texts (`describe()`, `src/host/core/Instance.cpp`); `tests/Vst3PluginTests.cpp` checks it with the tests' VST3 effect's Invert. It would go if JUCE's VST3 host said `isBoolean()` for a one-step parameter.

**W58. A meter a plug-in has as a parameter isn't taken for a value set.** JUCE's VST3 host tells what a VST3 outputs to its host as it processes (the process call's `outputParameterChanges`) as a change of the parameter, to the parameter's listeners on the thread that plays it (`setValueWithoutUpdatingProcessor()` after `process()`, `juce_audio_processors_headless/format_types/juce_VST3PluginFormatImpl.h`), and keeps a parameter's flags to itself but `kCanAutomate` (`isAutomatable()`): a read-only meter's changes (VST3's `kIsReadOnly`, which can't be automated) can't be told apart from values the plug-in set. Taken for values set in the plug-in's window, they wrote into the song, made it unsaved and had the plug-in's state asked again, for as long as the meter moved. The helper says nothing of a change of a parameter that can't be automated told on the thread that plays the instance (`Instance::parameterValueChanged()`, `src/host/core/Instance.cpp`); one the plug-in's window sets comes on the message thread (a VST3's `performEdit()`) and is told. A parameter that can't be automated and that the plug-in itself sets as it plays (one learned to a MIDI controller) isn't told either. It would go if JUCE's parameters said they are read-only, or JUCE told output changes apart.

**W60. A MIDI program change sets a VST3's program.** VST3 has no MIDI program change event: a host maps one to the plug-in's program parameter (the one flagged `kIsProgramChange`). JUCE's VST3 host hands it on only as a legacy MIDI controller event (`MidiEventList::createProgramChangeEvent()`, `juce_audio_processors_headless/format_types/juce_VST3Common.h`), which few plug-ins read. The helper's audio thread leaves the program a block's program change asks for in an atomic, and its message thread sets it with `setCurrentProgram()` at its next tick, as the song's own choice (`setProgramPlayed()`, `src/host/core/Instance.cpp`); a render's block that holds one waits for it to be set, so that it plays from that block's start in every render. A VST3 built with JUCE reads the legacy event back as a MIDI program change, so it gets the program twice, the same both times. `tests/Vst3PluginTests.cpp` checks it with the tests' VST3 synth, which reads no program change. It would go if JUCE's VST3 host set a VST3's program parameter for a MIDI program change.

### The song

**W30. Files written whole by Phazite, not `File::replaceWithData()` or `replaceWithText()`.** JUCE's two functions don't look at the result of their own write before they move what was written into the file's place, and return true (`juce_core/files/juce_File.cpp`); and a `FileOutputStream` that closes doesn't ask for its bytes to reach the disk. On a full disk that left a project file cut short where a whole one was, and Save said it worked. `writeWholeFile()` (`src/model/base/WholeFile.h`) checks every write and the stream's status, flushes, compares the size on the disk, then replaces the file; the project file, the autosave, the versions' files, presets, the library's facts file and the run marker are written with it. It would go if JUCE's functions failed on a failed write and flushed.

**W35. A link in a project's folders told apart by where it leads, not by `File::isSymbolicLink()`.** On Windows `isSymbolicLink()` is true for any reparse point (`juce_core/native/juce_Files_windows.cpp`), and the folders and files OneDrive or Dropbox keep are reparse points too, so `RangedDirectoryIterator` with `FollowSymlinks::no` doesn't go into them. A project's first save and Save As walk its folders themselves and leave out only an entry whose `getLinkedTarget()` is another place than the entry (`isLinkElsewhere()`, `src/model/project/Project.cpp`; `src/model/project/internal/Project.h`): a symbolic link or a junction, which could lead anywhere, or round to the project itself. It goes when JUCE tells a link from other reparse points.

**W36. A project file is checked to be readable before it is backed up.** On Linux, `File::copyFileTo()` opens the file it copies and reads from the stream without checking that it opened (`copyInternal()`, `juce_core/native/juce_CommonFile_linux.cpp`), which `FileInputStream::read()` asserts against; the copy then fails as it should. `Project::backUpProjectFile()` asks `hasReadAccess()` first and reports the backup as failed (`src/model/project/Project.cpp`); CI's linux-debug tests met the assertion with a project file no one may read (2026-11-14).

**W37. A full path from a file made a file without JUCE's assertion.** On Windows `File::isAbsolutePath()` is true for a path from a root with no drive ("\Sounds\Kick.wav", or a full path of a Mac's or Linux's, as a project from another computer can hold), and `juce::File`'s constructor asserts for such a path before it takes it for one on the current drive (`parseAbsolutePath()`, `juce_core/files/juce_File.cpp`). `makeFileOfFullPath()` (`src/model/base/WholeFile.h`) makes the same file without the assertion, where the model makes a file of a path that a project, a preset or a version holds; the fuzzer met the assertion with many rounds (the nightly run, 2026-11-15).

**W38. JSON read without the numbers JUCE's parser can't count.** `juce::JSON::parse()` counts the digits a number starts with up in a 64-bit integer before it knows whether they fit (`JSONParser::parseNumber()`, `juce_core/json/juce_JSON.cpp`), and reads an exponent's digits into an `int` the same way (`CharacterFunctions::readDoubleValue()`, `juce_core/text/juce_CharacterFunctions.h`): a whole number past the largest of 64 bits, or an exponent of ten digits or more, overflows a signed integer, which is undefined behaviour (in practice a wrong number). A preset, a keymap or a download from others can hold one; the fuzzer found it with many rounds under UndefinedBehaviorSanitizer (the nightly run, 2026-11-15). `phazite::parseJson()` (`src/model/base/Json.h`) looks through the text first, outside its strings, and takes one with such a number for no JSON; every JSON text Phazite reads goes through it (`tests/JsonTests.cpp`). An exponent as long in any text read as a number reaches the same reader through `String::getDoubleValue()` (a project file's properties, a version's pieces and a DAWproject's attributes, all XML): `hasExponentTooLongToRead()` and `makeExponentReadable()` (`src/model/base/Json.h`) tell one as that reader would take it, and make it the same number in a text it reads (past every double's, or 0), as a song loads before any of its numbers is read (`makeExponentsReadable()`, `src/model/project/internal/Project.h`, for the properties `Schema.h` says hold numbers: a name stays), as a version's pieces are joined (`src/model/versions/SongPieces.cpp`) and as a DAWproject is read (every attribute but a name, `src/model/project/DawProject.cpp`); the fuzzer writes such exponents (`makeExtremeNumber()`, `tests/Fuzzer.cpp`; known bug 170, 2026-11-15). Goes when JUCE's readers check before they count.

**W41. A DAWproject's zip written by Phazite, and refused before it is written where a zip without ZIP64 can't hold it.** `ZipFile::Builder` writes every entry's sizes and place, and the central directory's, in 32 bits, and the count of entries in 16, without ZIP64 (`writeToStream()`, `juce_core/zip/juce_ZipFile.cpp`), so an archive of 4 GB or more, or of more than 65,535 entries, came out damaged and the export said it worked (known bug 106). It also holds each entry whole in memory before it writes it, goes on past a write that failed (it looks only at whether a source could be read: `writeData()`), and can't be stopped, so a DAWproject export cancelled while its archive was written waited for the rest of it, gigabytes perhaps (the threading audit, 2026-11-20). `writeDawProject()` (`src/model/project/DawProject.cpp`, `ArchiveWriter`) writes the zip itself, in the same 32 bits: each file stored, copied a part at a time, its CRC and sizes written into its local header once it is all there, every write checked, and a cancel asked before each part, which leaves neither the archive nor its temporary file; the texts and presets packed with JUCE's `GZIPCompressorOutputStream`. `checkArchiveFits()` (`src/model/project/internal/DawProject.h`) adds up what the writer will write (each entry's headers, a stored entry's bytes, a packed one's at most as deflate can grow it) and `writeDawProject()` refuses past either limit before anything is written, saying to export the audio beside it or fewer tracks; the written file is checked once more against 4 GB. At most 65,534 entries and fewer than 0xFFFFFFFF bytes, as a reader takes those for ZIP64's marker; and the export counts its bounces as large as they can render and refuses before rendering any (`checkDawProjectFits()`). `tests/DawProjectTests.cpp` reads the archive back with JUCE's reader and checks each entry's CRC. Goes when JUCE's builder streams, stops and writes ZIP64.

**W56. The undo history's redo steps and its oldest steps, kept beside JUCE's (*JUCE's insides*).** `juce::UndoManager` puts the redo steps aside as a step is performed while there are some, empties what it put aside only then, and appends all it holds whenever a step is taken back alone by `undoCurrentTransactionOnly()` (`moveFutureTransactionsToStash()`, `restoreStashedFutureTransactions()`, `juce_data_structures/undomanager/juce_UndoManager.cpp`); `clearUndoHistory()` leaves it too. So after an Undo and an edit, a drag's Escape, a trial put back (Swap's) or a version closed again where there was nothing to redo brought back the redo step thrown away, which Redo offered and could apply to a tree it doesn't fit. Phazite counts the redo steps JUCE holds past the song's own, always the last (`Song::History::staleRedoSteps`, `src/model/base/Song.h`; `takeBackAlone()` and `settleRedoSteps()`, `src/model/commands/Undo.cpp`), and Redo, its name, its enabled state and Undo History reach none of them (`canRedo()`, `getHistorySteps()`). Three things more lean on how JUCE does it: a step can't be taken back alone once another began on top of it (`undoCurrentTransactionOnly()` asks that the last began nothing yet), so a version open has the song's redo steps done again first and is put back with undos alone (`Trial::holdHistory()`, `putBackHeld()`); JUCE drops its oldest steps only as one is performed, never as its limit falls (`dropOldTransactionsIfTooLarge()`), which the two steps more kept while a version is open rely on, and the one more for each step begun inside another on top of it (`Song::setShowingOther()`, `Trial::stepBegins()`), so that the steps on top of it are counted from where its own ended (`Trial::countStepsOnTop()`); and a branch an edit makes from a version open starts its history at that edit by a change of nothing performed into it while the edit's steps alone are kept (`startHistoryAgain()`). `tests/VersionsOpenTests.cpp` checks each. It would go if JUCE emptied what it put aside when it starts a step with nothing ahead, and could drop the steps under the last one.

**W8. A property set without an undo step only when its value changes.** Without an `UndoManager`, `ValueTree::setProperty()` compares the value's type too (`NamedValueSet::set()`, `juce_core/containers/juce_NamedValueSet.cpp`; `juce_data_structures/values/juce_ValueTree.cpp`), so the number 5 over the text "5" read from a file is a change its listeners hear; with one, it compares values alone. The two stores that write without one compare first (`storeProperty()`, `src/model/plugins/PluginInstances.cpp`; `store()`, `src/model/mixer/Mixer.cpp`); they could be one function.

**W62. The song's keeper of its values performs undoable actions from inside the tree's own (*JUCE's insides*).** The song's clips, a MIDI clip's notes, its tempo map and its chord lane are values beside the song's tree (`src/model/base/internal/SongValues.h`), and the keeper (`SongValues::Keeper`, `src/model/base/SongValues.cpp`, which asks each area's part of it in turn: `ClipsArea.cpp`, `TempoMapArea.cpp`, `ChordLaneArea.cpp`) keeps them and the tree together for every change of the tree: as a track goes from the song's track list (alone, in a folder, the list itself) it erases its clips and their notes from the areas (`ValueArea.h`: an action of each area's, performed through the song's `juce::UndoManager`), remembering them with the track's element; as the same element comes back (JUCE moves a track by taking it out and putting it in again) it gives them back; and as a track comes into the song with its clips' elements, which only a safety net leaves to it, it reads them into the areas and removes them from the tree with the same undo manager (never a clip's element added to a track by itself, which the step's Undo, taking the tree's change back first, would find gone: the keeper refuses one, a JUCE assertion); and the same of a TEMPOMAP that comes into the song with TEMPO and TIMESIGNATURE elements, read into the tempo map's area and taken out of it (a lone entry added to the song's TEMPOMAP is taken in only outside the history, refused in a step for the same reason), and of a CHORDLANE that comes in with CHORD and CHORDKEY elements, read into the chord lane's area (a lone CHORD or CHORDKEY the same as a lone tempo); all from inside the tree's `valueTreeChildAdded()` and `valueTreeChildRemoved()`, which JUCE calls from inside the `juce::UndoableAction::perform()` of the tree's own action. The documentation of `UndoableAction::perform()` and `undo()` warns against calling `UndoManager::perform()` from inside them; the manager refuses it only while it undoes or redoes (`isPerformingUndoRedo()`, whose callbacks the keeper ignores, as the areas' own actions move them then), and otherwise performs the inner action and adds it to the current transaction before the outer one, which it adds once its `perform()` returns (`juce_data_structures/undomanager/juce_UndoManager.cpp`). What is relied on: that the inner actions join the step in progress (or begin it, under the step's name), and their place before the outer: Undo takes the tree's change back first and the areas' after it, which is one reason why no tree callback reads the clips' area, with no exception (SongValues.h: a listener of the tree reads the clips at its later moment); the other is that JUCE calls a tree's listeners handle by handle in the order of the handles' addresses, so another listener of the song's root may hear of a moved track before the keeper gives it its clips back. A listener told by an area's undo finds the track in the song again (or gone), as it is told by a step's. It would break if JUCE refused a nested `perform()` (the areas' and the tree's changes would be lost), added an action to its transaction before performing it (Undo's order reversed), called the tree's listeners after the action, or coalesced an action across the two. `tests/SongValuesTests.cpp`'s keeper cases (each rule with its Undo and Redo, under `UndoCheck`), `tests/SongValuesTempoTests.cpp`'s and `tests/SongValuesChordsTests.cpp`'s, `tests/SongValuesClipsTests.cpp` (a track with clips deleted and duplicated, with its Undo and Redo), `tests/ValueAreaTests.cpp` and the model's fuzzer (`tests/ModelFuzzTests.cpp`, which checks the song's values after every operation and its undo) would show it. It goes when the song's tracks are values themselves (roadmap step S5.20), and nothing of the tree holds what a value must follow.

### Devices

**W54. ## The build

**B1. GCC's dangling-reference warning off for one unit of JUCE's.** GCC 13 and later read `opt.getButtons().front()` in `juce_gui_basics/lookandfeel/juce_LookAndFeel_V2.cpp` as a reference to a temporary; nothing dangles. The warning is off for `juce_gui_basics_2.cpp` alone (`CMakeLists.txt`).

**B2. JUCE's recommended config flags with GCC and Clang only.** On MSVC they add `/MP` (`extras/Build/CMake/JUCEHelperTargets.cmake`), which MSVC refuses beside the `/showIncludes` that Ninja needs (warning D9030 for every file); CMake's own defaults give MSVC the rest (`CMakeLists.txt`).

**B3. juceaide built with Phazite's toolchain.** JUCE configures its `juceaide` helper in a CMake run of its own, without the toolchain file, and keeps that folder even after `--fresh` (`extras/Build/juceaide/CMakeLists.txt`). Phazite hands the toolchain on through the environment (`CMakeLists.txt`, `CMakePresets.json`, `cmake/toolchains/windows-msvc.cmake`), deletes the folder when the compiler or the toolchain changes, and stops if it was configured without the toolchain (`cmake/PhaziteHelpers.cmake`).

**B4. The installer takes the app's icon from juceaide's folder (*JUCE's insides*).** juceaide makes the app's icon as CMake configures (`extras/Build/CMake/JUCEUtils.cmake`); the installer target reads it from the app's generated sources by its name, `icon.ico`, and the logo is a configure dependency, so that a change to it makes the icon again (`CMakeLists.txt`).

**B5. linux-tsan in RelWithDebInfo, with -Wno-tsan.** ThreadSanitizer needs optimisation, and JUCE forces `-O0` in Debug (`JUCEHelperTargets.cmake`); GCC warns that TSan doesn't model `atomic_thread_fence()`, which JUCE (`juce_core/memory/juce_Atomic.h`) and Phazite's engine use. In `CMakePresets.json`, which can't hold a marker.

Build choices that aren't workarounds: JUCE compiled once, in `phazite_core` (`phazite_use_core()`), because JUCE's modules are interface libraries that compile into every target linking them, as JUCE advises for code shared between targets; JUCE's options on `phazite_core`, among them `JUCE_USE_CURL=0`, which leaves Linux without HTTPS, so that Phazite Sounds' download and the update check refuse there until Phazite builds with curl (docs/design.md); `using` declarations where GCC's `-Woverloaded-virtual` meets JUCE's overloaded virtual functions; and parallel compiles limited by the memory JUCE's large units take (`cmake/PhaziteHelpers.cmake`).

**T8. A damaged file is nothing Phazite did wrong, Release builds compile no assertions, and Phazite doesn't write readers of its own for assertions that harm nothing, so the fuzz cases declare them (`ExpectedAssertion`, `tests/TestHelpers.h`), each by its file and line, where it is expected: the zip's date around the DAWproject case's reading alone (`tests/FuzzTests.cpp`), as any local `Time` made of a date that isn't one would raise the same assertion elsewhere; the others for every fuzz round (`readersAssertions`, `tests/Fuzzer.cpp`). Phazite's own readers compare tags exactly (`getTagName() ==`) and never use a zip entry's date. A Release build does nothing undefined with such a date: `parseFileTime()` hands `Time`'s constructor fields of a few bits each (a year from 1980 to 2107, a month from -1 to 14, a day from 0 to 31, an hour from 0 to 31, a minute from 0 to 63, a second from 0 to 62), `mktime_local()` gives them to the C library's `mktime()`, which the C standard lets take fields outside their ranges and brings into range (or answers -1 for a time it can't represent, which JUCE multiplies by 1000 in 64 bits), and the date, whatever it comes to, goes unused. Until 2026-11-15 this was open question Q7; known bug 149.

## Correct patterns

Code shaped by JUCE that uses it as documented. It needs no marker, and nothing at an update.

- **Threads:** `stopThread (-1)` once what the thread waits on is woken, JUCE's documented wait without a limit; where the system allows no real-time threads, the highest priority when `startRealtimeThread()` returns false (`src/devices/core/AudioThreads.cpp`).
- **Audio buffers:** a part's output buffer is cleared through its channels' pointers, never by `AudioBuffer::clear()`, which JUCE documents as skipping a buffer it marked clear: writing through the pointers doesn't unmark it (`src/engine/nodes/PartOutput.h`).
- **Child processes:** `juce::ChildProcess` isn't safe from several threads (on Linux `isRunning()` reaps the child), so a helper's process is looked at by one thread at a time (`src/sandbox/client/Helper.h`).
- **Downloads:** the update check follows redirects itself, as JUCE would follow one to `http://` (`src/services/Updates.cpp`).
- **Keys over plug-ins in their helper:** a `WH_GETMESSAGE` hook catches the keys on their way to a plug-in's own native windows, as JUCE's own plug-in client does (`src/host/core/Editor.cpp`).
- **What JUCE leaves to the app:** a Bluetooth output found by its device's name (`src/model/engine/AudioDevices.cpp`), devices plugged in found by comparing lists (`AudioDeviceWatch.cpp`), oversampling a sample at a time with JUCE's half-band design (`src/devices/dsp/Oversampling.cpp`), memory shared between processes (`src/sandbox/core/SharedMemory.h`) and a queue that several threads write into (`src/engine/core/EventQueue.h`).
- **Choices over JUCE's own:** r8brain-free-src in place of JUCE's Lagrange interpolator (docs/archive/dsp-audit.md), and the song as Phazite's own text with standard base 64, not JUCE's XML writer and its own base 64 (`src/model/base/internal/SongText.h`).
- **Devices and files:** inputs opened only as the tracks need them (`useDefaultInputChannels = false`, `src/model/transport/AudioRecorder.cpp`); a device set up without taking it for the user's choice (`setAudioDeviceSetup (setup, false)`, `PlaybackHost.cpp`); a file deleted before a `FileOutputStream` writes it, as a stream adds to what is there (`Export.cpp`, `OfflineRender.cpp`).
- **The audio thread:** what JUCE's device manager and plug-in hosting do there is in docs/realtime-audit.md (findings 3 and 9).
- **Devices' windows:** each floats over the main window, above it but not above other apps, minimised and moved with it, through `TopLevelWindow::setAssociatedComponent()` (`src/app/PluginWindow.cpp`).
- **Windows and the focus:** the title bar's hit test by bounds alone, as JUCE warns that `contains()` there can recurse, with the style flags JUCE gives its own title bar's buttons added back for Phazite's (`findControlAtPoint()`, `src/app/MainWindow.cpp`); the shell's focus traverser, which JUCE asks where the focus goes when a focused part hides (`AppShell.cpp`); a value field in the window's content component, as JUCE asserts when children are added to the window itself, or in the dialog or popup that has the keys (`Controls.cpp`); and a value field that finishes on Return, Escape or a lost focus at once, by overriding `keyPressed()` and `focusLost()`, as JUCE's `onReturnKey` and the like come a message later on purpose (`Controls.cpp`); and the search field of the command palette, the plug-in picker and the branch picker taking the keys a message after its call-out opens (`CommandPalette.cpp`, `PluginPicker.cpp`, `BranchPicker.cpp`): JUCE's call-out already gives them to its first control as it goes modal (`Component::enterModalState()`), so this only makes sure of it.
- **The mouse and the keys:** an editor's `UseListener`, not the editor listening to itself, as JUCE's listeners hear a component's events besides it (`TimelineEditor.cpp`); `onUsed` on a press, as JUCE tells focus changes a message later (`TimelineEditor.h`); held keys by `keyStateChanged()` and `isKeyCurrentlyDown()` (`KeyDispatcher.cpp`); keymap changes saved by command ID, as JUCE's command numbers follow the order commands were registered in (`KeymapStore.cpp`).
- **Menus, tabs, labels and buttons:** a menu's result checked to be over 0, as 0 is a menu dismissed; one tab holder for each area, as `clearTabs()` hides the view it showed (`Panels.cpp`); JUCE's documented order of a label's callbacks (`SectionsStrip.cpp`) and a radio button's `onClick` for the button turned off (`Welcome.cpp`).
- **Drawing:** the look's overrides, JUCE's hooks for its controls' look (`LookAndFeel.cpp`); a theme switch through `applyColourToAllText()` and the colours set again (`LookAndFeel.cpp`, `MainWindow.cpp`); `Path::isEmpty()` read as JUCE documents it, true for a path of starts alone (`DeviceGraph.cpp`); `setBufferedToImage()` called only when the choice changes, as each call with true makes a new picture (`PlaylistRows.cpp`); a drag's image made as a software image, quick to make (`StripParts.cpp`); the playhead moved at the display's frames by a `VBlankAttachment` (`TimelineEditor.cpp`); Lucide's `currentColor`, which JUCE reads as black (`Icons.cpp`; until 2026-11-11 the icons' text was changed to black before JUCE read it, which JUCE 9 doesn't need).
- **Typed values:** text without a digit, ignored by a knob, as JUCE reads what isn't a number as 0 and checking what was typed is the app's job (`Controls.cpp`); and the field a value is typed in without a right-click menu, as it lives only while it has the keys, which a menu would take, with Ctrl+C and Ctrl+V working in it (`setPopupMenuEnabled (false)`, `Controls.cpp`; the owner's choice, 2026-11-11).
- **Late notifications:** a change a slider sends asynchronously, as JUCE documents `sendNotificationAsync`, ignored once the piano roll's transform bar has closed (`PianoRollLanes.cpp`).
- **The song against its saved copy** (`src/model/project/internal/Project.h`), which also finds edits undone by hand.
- **An area of the song held as a value, in the song's undo history** (`ValueArea`, `src/model/base/internal/ValueArea.h`): the area's one action in a step is Phazite's own `UndoableAction`, given another value after while its step is in progress, which it finds among `UndoManager::getActionsInCurrentTransaction()`, as JUCE documents both. The area keeps its own action rather than JUCE's coalescing (`createCoalescedAction()`), which joins an action only with the one performed right before it: the tree's, in a step that changes both. Measured by the spikes: `clearUndoHistory()` leaves the redo steps JUCE put aside last (W56), so one action of an area and its two values can outlive a clear until redo steps are put aside again. That needs no code of its own: it is memory held a while, Redo never reaches those steps (W56), and the actions share the area's state, so one that outlives the area changes only what is left of it and tells no one.
- **Memory:** a helper's private working set, measured for the benchmarks (`src/host/core/Platform.cpp`); and DbgHelp set up once for the process, as JUCE sets it up too (`tests/AudioThreadMonitor.cpp`).

Some code works around the operating system, not JUCE: the tests' timers, which Windows 11 slows in a program none of whose windows can be seen (`keepTimerResolution()`, `tests/TestMain.cpp`), and waits that spin rather than yield on the audio thread, where Windows' scheduler can lose 16 ms (docs/realtime-audit.md, finding 24). PhaziteHost's timers are probably slowed the same way while none of its plug-ins' editors shows, which harms nothing: its audio threads wait on the bells Phazite rings, not on timers (not measured).
